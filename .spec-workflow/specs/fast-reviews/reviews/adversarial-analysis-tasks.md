# Adversarial Analysis — fast-reviews/tasks (v1)

You commissioned a tear-down of `tasks.md`. Below: five sections, each citing actual task text and concrete failure scenarios. Closing deliverables follow.

## 1. Task atomicity — bundled work hiding inside single tasks

- **Task 1 is two tasks pretending to be one.** The success criterion gives the game away: "Constant defined once, methodology renders identically to before for existing phases, constant is exported or module-visible". Step 1 is a data extraction (define `PHASE_ATTACK_ANGLES`); step 2 is a refactor of `getAdversarialReviewMethodology()` to interpolate from it. A developer who finishes the constant but doesn't get the interpolation byte-identical gets blocked on a snapshot diff that has nothing to do with what they were primarily doing. Worse, the byte-identical guarantee requires preserving the exact current pipe spacing in the markdown table at lines 272–277 — see Task 1's own `_Restrictions_` "the output of getAdversarialReviewMethodology should be byte-identical for existing phases — verify via snapshot". There is no snapshot test in Task 4, so this verification has no home. Split into 1a (constant + unit test that the data shape matches the current rows) and 1b (interpolation + snapshot of `getAdversarialReviewMethodology()` output).

- **Task 3 bundles three unrelated changes.** It (a) integrates `fs.writeFile`, (b) rewrites `nextSteps`, and (c) updates the tool `description` at the top of the file. The description change has no test in Task 4 and is not pinned by any acceptance criterion in `requirements.md` — Requirement 1.6 names `nextSteps` specifically, not the tool description. A developer can land the file write and `nextSteps` rewrite, ship the PR, and silently leave a stale `description: 'Returns the methodology, output paths, and context needed to generate a tailored adversarial prompt and execute it via a fresh-context subagent. The agent writes the prompt...'` (current text, lines 9–17 of `adversarial-review.ts`) that contradicts the new flow. Move the description update to its own task, or pin it with an explicit test that asserts the description string contains "scaffold" / "placeholder".

- **Tasks 7 and 8 are the same change split across two PRs.** Task 7 adds `hasHygieneSignals` to `buildReviewMethodology`'s signature and threads it through. Task 8 makes the body actually branch on it. Between them, the parameter is dead weight — typecheck passes, tests pass (because Task 8's tests don't exist yet), and the methodology is unchanged. The cited `_Leverage_` of Task 8 — "existing conditional section pattern in buildReviewMethodology (see hasTechSteering / hasPriorReviews branches)" — confirms the natural shape: add the parameter and use it in one commit, the way `hasTechSteering` and `hasPriorReviews` were originally added together. Merge.

- **Task 3's Restrictions block smuggles in a behavioral spec.** The line "do not bypass error paths — write failure must propagate as success:false" is not a restriction — it is the very behavior Requirement 1.8 mandates. Hiding it in `_Restrictions_` means it is invisible to a reader scanning success criteria and untestable without explicit test coverage. It belongs in Task 3's `_Success_` clause and should drive a Task 4 test ("Write failure: simulate by making `reviewsDir` read-only") — which Task 4 already lists, so the restriction should be promoted to the success criterion and crossed off as a restriction.

- **Task 5 bundles four regex behaviors plus error-handling plus size-limit plus concurrency.** "skips files that fail `stat` / `readFile` or exceed 1 MB, splits content on `\n`, and applies four regexes" is implementing four detectors, two failure modes, a size budget, and a `Promise.all` concurrency pattern. The success criterion "fast enough to scan 50 files of 500 lines in <200ms" cannot be checked except by adding a perf assertion that Task 6 does not include. Split the regex set from the error/size handling, or at minimum add a Task 5b for the perf assertion and put the four regex bodies into a `PATTERNS` constant the test can iterate over.

## 2. Ordering — intermediate states that cannot pass tests or build

- **Task 7 → Task 8 leaves a dead parameter.** Task 7's `_Success_` says "data.hygieneSignals present in every successful prepare response, length-based flag threaded correctly to methodology builder, no existing tests broken". But "threaded correctly" does not mean "consumed correctly". After Task 7 alone, `buildReviewMethodology(taskContext, hasTechSteering, hasPriorReviews, hasHygieneSignals)` accepts the flag and ignores it. If a reviewer takes Task 7 as a standalone PR (which the linear numbering implies they could), they ship a code smell: a 4th parameter with no readers. TypeScript will not flag it because parameters are not "unused" the way locals are. Either combine 7 and 8, or have Task 7 *not* add the parameter and have Task 8 add the parameter + use it together.

- **Task 9's tests assume Task 8 is done.** Task 9(c) says "methodology contains the triage directive when signals are present". Task 7 alone does not produce a triage directive — Task 8 does. So if Task 9 tests are written against the post-Task-7 state, test (c) fails; if written against the post-Task-8 state, the tests in test (c) cannot land in the same PR as Task 7. The linear numbering 7→8→9 is fine if these are all in one PR. Call this out in the document so a developer doesn't try to ship Task 7 and Task 9 on its own branch.

- **Linear numbering hides the actual dependency graph.** Task 4 sits after Task 3 and before Task 5, but Task 5 (hygiene-signals utility) does not depend on Tasks 1–4 in any way — they touch different files (`src/tools/adversarial-review.ts` vs. `src/core/hygiene-signals.ts`). The real graph is `1→2→3→4` and `5→6→7→8→9`, joined only at Task 10. A developer reading 1→10 will assume each task blocks the next. Add a "Dependency graph" header at the top of `tasks.md` showing the two parallel tracks, or restructure the list into "Track A: adversarial scaffold (tasks 1–4)" and "Track B: hygiene signals (tasks 5–9)".

- **Task 10's manual verification self-mutates the workspace under review.** Step 3: "invoke `mcp__spec-workflow__adversarial-review` against `.spec-workflow/specs/fast-reviews/requirements.md` (v1), inspect the written prompt file, then invoke again (v2) and inspect." This writes `adversarial-prompt-requirements.md` and `adversarial-prompt-requirements-r2.md` into the very `.spec-workflow/specs/fast-reviews/reviews/` directory that already contains the actual review artifacts for this spec. If the spec authors are also using `adversarial-review` for normal review of `requirements.md`, the manual test pollutes that workflow's version counter (next "real" review of `requirements.md` becomes v3+ with no v1/v2 of substance). Either point the manual test at a sandbox spec, or have the test write to a temp `.spec-workflow` and assert on the result there — never against the live spec under development.

- **Line numbers are still consistent — but only just.** Task 1 modifies lines 237–366 of `adversarial-review.ts` (the methodology body). Task 3 references "current line ~131" (the path-computation block ending at the `latestAnalysisPath` ternary). Confirmed: line 131 in the current file is `: null;` and line 237 begins `getAdversarialReviewMethodology()`. They are far apart, so Task 1 cannot shift Task 3's anchor — but if a developer does Task 1 and *expands* the methodology section past line 366, Task 5–9 anchors in `review-task.ts` (lines 116–228, 177, 414) are untouched because they are in a different file. This is fine. The risk is that the next iteration of this spec might add more cross-file work; the line-number anchors will rot fast. Convert to symbolic anchors ("after the `latestAnalysisPath` assignment") in future task lists.

## 3. Requirement coverage — written requirements with no task that satisfies them

- **Requirement 1.7 has prose coverage but no test.** R1.7: "WHEN an override methodology is configured via `.spec-workflow/adversarial-settings.json` THEN the scaffold SHALL still be written". Task 3's `_Success_` says "adversarial-settings.json override still works (data.methodology still populated from override when configured)" — that's the *override* behavior, not the *scaffold-still-written* behavior. Task 4 lists exactly five tests:
  1. v1 (fresh spec) — placeholders correct
  2. v2 — both placeholder blocks
  3. decomposition phase
  4. unknown phase
  5. write failure
  None of them is "override + scaffold both present". Add Task 4f: write `adversarial-settings.json` with a `reviewMethodology` override, run `adversarialReviewHandler`, assert (a) the scaffold file exists at `promptOutputPath`, (b) `data.methodology` equals the override string, (c) the scaffold file content does not equal `data.methodology` (i.e., the override didn't replace the scaffold).

- **Requirement 2.6's "exceed 1 MB" test is hand-wavy and may not exercise the code path.** Task 6 says "oversize file (mock via writing > 1 MB of text or by stubbing stat)". Writing a real 1 MB file in CI is fine on disk and time, but it makes the test obvious and slow (~1 MB temp dir per CI run). Stubbing `stat` alone is wrong: the code path is `stat → check size → readFile`. If you stub `stat` to return size > 1 MB but leave `readFile` real, and `readFile` is what actually short-circuits via the size check, you're testing the wrong gate. Specify the exact mock surface: stub `stat` to return `size: 1024 * 1024 + 1`, assert that `readFile` is *not* called for that file (use a spy on `fs.readFile`), and that the function still returns signals from the other (real) files. Without this, "skipped silently" can be vacuously true because the regex finds nothing on the real file content.

- **Performance NFRs have no tests at all.** "Scaffold generation + file write completes in < 50 ms" and "Hygiene signal computation completes in < 200 ms for 50 files × 500 lines" are non-functional requirements. Task 5's `_Success_` notes the 200ms target but no Task 5/6 test asserts it. No task contains a `performance.now()` measurement. Either:
  - Add a perf-assertion test in Task 6 (timed loop of 50 files × 500 lines, assert wall time < 200 ms), or
  - Explicitly downgrade the NFR in `requirements.md` to "best-effort, not asserted in CI" so it isn't a coverage gap.
  Right now the doc claims an NFR the code never proves.

- **Requirement 2.2's "absolute path" precondition is not enforced.** R2.2: "fields `file` (absolute path)". `computeHygieneSignals(files: string[])` receives whatever paths the caller passes. Task 7 says "After `allFiles` is computed (current line 177)..." — and `allFiles` is built from `latestLog.filesModified` and `latestLog.filesCreated`. Examine `ImplementationLogManager.getTaskLogs()` output: `filesModified` and `filesCreated` are whatever strings were passed to `addLogEntry`. The existing `review-task.test.ts` line 42 passes `'src/handler.ts'` — a relative path. So with the current wiring, R2.2's "absolute path" promise is a fiction. Either resolve to absolute in `handlePrepare` before calling `computeHygieneSignals`, or downgrade R2.2 to "whatever path string the implementation log provided". Add a test asserting which.

- **Requirement 1.5's "appropriate to that phase" is untestable as written.** R1.5: scaffold "SHALL render a persona opening and attack-angle reference appropriate to that phase". "Appropriate" has no objective measure. Task 4(c) says "decomposition phase: scaffold... contains decomposition-appropriate persona/attack-angle." How does the test verify "appropriate"? The only deterministic check is "the scaffold contains the exact `attackSurface` string from `PHASE_ATTACK_ANGLES['decomposition']`". Spell that out. Otherwise the test will just check `scaffold.includes('decomposition')` and pass trivially.

## 4. Completion criteria — success conditions that are unfalsifiable or evade verification

- **Task 1's "renders identically" has no enforcement.** `_Success_`: "methodology renders identically to before for existing phases". The natural enforcement is a snapshot of `getAdversarialReviewMethodology()` taken before Task 1 begins, asserted unchanged after. Task 4 — explicitly the "test task" — does not include this snapshot. The developer is left to either (a) write the snapshot test inside Task 1 (violating the "test task is Task 4" pattern), (b) skip it and hope, or (c) add it ad-hoc. Resolve by either moving the snapshot into Task 1 explicitly or adding it as Task 4(0).

- **Task 2's "valid generic scaffold" is undefined.** `_Success_`: "unknown phases produce a valid generic scaffold". What is "valid"? Contains the same H1, target document, analysis dimensions placeholder, closing deliverables, and output sections? Yes — but the criterion doesn't say so. Task 4(d) only checks "scaffold still written, contains a generic persona string, handler still returns success." That does not assert structural completeness. A bug where the unknown-phase branch emits only the H1 and persona, missing the placeholder block, would pass Task 4(d). Tighten Task 4(d): assert all five sections are present and the `PLACEHOLDER:ANALYSIS_DIMENSIONS` block is intact.

- **Task 8's "byte-identical when absent" diverges from Task 9's actual test.** Task 8 `_Success_`: "when absent, the methodology is byte-identical to before; verify via snapshot or string comparison in tests". Task 9(b): "prepare on a clean task returns `data.hygieneSignals: []` and methodology contains the full fallback item 9". "Contains the full fallback item 9" is a substring check, not a byte-identity check. The methodology could grow an extra trailing newline, an extra space in item 8, or a reordering of items 1–8 and Task 9(b) would still pass. Either change Task 8 to "the substring of item 9 matches the current text" (matching Task 9), or add a true snapshot to Task 9(b).

- **Task 10's "reads as nonsensical to a human" is a vibe check.** `_Restrictions_`: "do not ship if the manual scaffolded prompt reads as nonsensical to a human". Who is the human? What does nonsensical mean? Is "this scaffold's persona feels weak" nonsensical, or just disappointing? This is a subjective gate that one reviewer can use to block a PR with no recourse. Either (a) define a checklist (e.g., "the persona is a human role title", "the placeholder block reads as a directive, not a fragment"), or (b) drop the criterion and trust the actual unit tests.

- **Task 5's `_Success_` includes a perf number that no test enforces.** "is fast enough to scan 50 files of 500 lines in <200ms". This success criterion is asserted by reading the docstring, not by the test suite. If a future change adds an `await new Promise(setTimeout(..., 50))` per file, the criterion silently breaks. See section 3 above — add a perf test or strike the line.

## 5. Edge cases the breakdown silently ignores

- **A line matching two patterns at once produces two signals.** Task 5 says "applies four regexes ... Each match produces one HygieneSignal". A line `// TODO: remove console.log(x)` will match both `/console\.(log|warn|error|debug|info|trace)\s*\(/` and `/\bTODO\b/`. The result: two signals on the same line, with the same `text`, differing only in `pattern`. Is this intended? The design says signals are advisory and the LLM triages, so two signals are not catastrophic — but no test in Task 6 exercises this case, and the user reading the prompt sees a doubled line. Add a Task 6 test for the "double match" case and decide explicitly: report both, or dedupe by `(file, line)` and tag the dominant pattern.

- **Files appearing in both `filesModified` and `filesCreated` cause double-scanning.** Task 7: `const allFiles = [...new Set([...latestLog.filesModified, ...latestLog.filesCreated])];` — wait, the existing code already wraps in `new Set(...)` (line 177 of `review-task.ts`). So *exact-string* duplicates are deduped. But if `filesModified` has `'src/foo.ts'` and `filesCreated` has `'./src/foo.ts'` or an absolute path, the Set won't dedupe. Combined with R2.2 (signals carry "absolute path"), this means the *output* signals could end up duplicated even though the *input* set is unique-by-string. Task 7 should canonicalize via `path.resolve(projectPath, p)` before passing to `computeHygieneSignals`, then the Set contains absolute paths and dedupes correctly. No task currently does this.

- **Windows line endings (`\r\n`) only mostly work.** Task 5: "splits content on `\n`". A line `console.log(x)\r\n` becomes `console.log(x)\r` in the split array. The regex `/console\.(log|warn|error|debug|info|trace)\s*\(/` matches at `console.log(` regardless of trailing `\r`. The `text` field after `.trim()` strips trailing `\r` (since `\r` is whitespace by `String.prototype.trim`). So the signal is correct. But for `\bTODO\b` followed by content like `\bTODO\b\r` — also fine, `\b` matches the boundary before `\r`. The genuine risk is *not* the regex match itself but the `text` truncation: if the line is exactly 120 characters of content + `\r`, the trim happens before truncation in the spec ("trim → truncate to 120"), so `\r` is gone before slicing. Confirmed: this works. Drop this concern unless a test exposes it.

- **Override + unknown phase precedence is unspecified.** A user with `adversarial-settings.json` containing `reviewMethodology: "..."` runs `adversarial-review` against `phase: 'bogus'`. R1.7 says scaffold is still written. Task 2 says unknown phase falls back to generic persona. The override only affects `data.methodology`, not the scaffold. So: scaffold is generic, methodology is the override text, neither references "bogus" phase. Is that the right precedence? The design does not say, the requirements do not say, no task tests it. Add a Task 4 test: override + unknown phase = scaffold uses generic persona, `data.methodology` equals override. Pin the behavior or it will drift.

- **Task 8's `category: 'hygiene'` directive is real and consistent.** Verified at `src/types.ts:203`: `category?: 'spec-compliance' | 'hygiene'`. The directive in Task 8 telling the LLM to "promote real leftovers to findings with `category: 'hygiene'`" is consistent with the existing schema. Existing item 9 in `buildReviewMethodology` (line 414) already says `Mark findings from items 7-9 with category: "hygiene"`. So the new directive does not introduce a schema mismatch — it reinforces the existing convention. **Fine. Drop this concern.**

- **`getMethodologyOverride` reads `adversarial-settings.json` from `workflowRoot` once per invocation.** Not raised in the breakdown but worth flagging: if a user adds an override mid-implementation, it kicks in next call. No task tests cache invalidation because there is no cache. Fine. Skip.

## Top 5 risks/gaps (ranked)

1. **Task 7 ships a dead parameter (Tasks 7, 8 split).** A developer landing Task 7 alone passes typecheck and tests, but `buildReviewMethodology` accepts a flag it ignores. Production consequence: a downstream PR that reverts Task 8 (or never reaches it) leaves a useless 4th parameter — code smell, possible lint flag, confusing for future maintainers. Merge Tasks 7 and 8 or rewire Task 7 to not modify the signature.

2. **Task 4 has zero coverage for Requirement 1.7 (override + scaffold).** Production consequence: a user with a legitimate `adversarial-settings.json` override runs `adversarial-review`, the implementation regresses such that the scaffold is no longer written when an override is present (because some future refactor short-circuits on override-detected). No test catches it; CI green; user gets the override methodology in `data.methodology` and an empty `promptOutputPath`. Add Task 4f.

3. **Task 10's manual verification writes into the live `fast-reviews` review directory.** Production consequence: the version counter in `.spec-workflow/specs/fast-reviews/reviews/` is incremented by a verification artifact, polluting the spec's own review history. Future readers of this spec see "v1, v2 (manual test), v3 (real review)" with no way to tell them apart. Point Task 10's manual test at a sandbox spec or a temp `.spec-workflow` directory.

4. **Performance NFRs (50 ms scaffold, 200 ms hygiene) are unenforced.** Production consequence: a regression that doubles hygiene scan time goes undetected because no test asserts the budget. The spec promises a perf number it cannot keep. Add a perf-assertion test in Task 6 or strike the NFR.

5. **`computeHygieneSignals` receives whatever path strings the implementation log contains, but R2.2 promises "absolute path".** Production consequence: a finding emitted to the LLM with `file: 'src/handler.ts'` (relative) — the LLM has no way to read it without knowing `projectPath`. The reviewing agent fails to open the file and reports a false negative. Resolve paths to absolute in Task 7 before calling the utility.

## Top 3 conclusions to challenge or reverse

- **Reverse: Tasks 7 and 8 should be one task.** The spec splits them under a "thread the parameter, then use it" model, which is a textbook pattern for *long-lived* refactors that need staged rollouts. This is not that — they ship in the same release. Splitting them creates an intermediate broken state (dead parameter), invites a partial PR that lands Task 7 alone, and forces Task 9 to assume Task 8 is done. The "thread first, use second" pattern only earns its keep when the threading takes risk that should land first, e.g. across a service boundary. Inside one function in one file, it is overhead. Merge.

- **Reverse: Task 10's manual verification should not run against the live spec under development.** The spec writes manual artifacts into `.spec-workflow/specs/fast-reviews/reviews/` — the same directory where the spec's own canonical review files live. This conflates "I am implementing this spec" with "I am reviewing this spec", and the implementation artifacts now look like review artifacts to anyone reading the directory later. The integration test should run against a disposable target (temp dir, throwaway spec). The current design seems clever — "test the tool by using the tool on the spec defining the tool!" — but it's a pollution vector and should be reversed.

- **Reverse: Task 1's "byte-identical methodology" guarantee.** The `_Restrictions_` of Task 1 say the output of `getAdversarialReviewMethodology` should be byte-identical for existing phases. This is a strong constraint that locks in current whitespace, current pipe alignment, and current row order. A real refactor of the table-as-string into table-from-data is unlikely to be byte-identical without contortions (the current markdown table uses `| Phase | Primary attack surface | Example angles |` formatting that depends on string lengths). A more honest constraint: "the rendered prompt with the new constant produces the same set of rows in the same order with the same content per row, but whitespace inside the table cells may differ." Then write a structural test (parse the markdown table, assert the row data) instead of a snapshot test. Otherwise Task 1 will spend hours getting the trailing-space situation just so.
