## Findings

### INFO: `none` note can follow an `unreadable` note, against the Data Models invariant
- **File:** src/controller/merge.ts:652
- **Issue:** The inline comment and design.md Data Models state `none` follows only a logged non-empty list, but the guard is `if (prior === undefined) return undefined`, which only suppresses `none` when there is no prior note at all. When the newest logged note is `new dependencies: <repo>#<n>: unreadable (<why>)` and a later poll reads deps as readable-but-empty, `prior` is defined and differs from `none`, so a spurious `none` note is written — contradicting the stated invariant and the code's own comment. Reachable: pass 1 base/head unresolvable locally (e.g. origin ref not yet fetched) -> `unreadable` note; pass 2 resolvable with no new deps -> `none` note. Impact: one extra benign ledger note on an unreadable->empty recovery; no effect on verdict, reasons, status or any wait (AC7 holds). There is genuine tension with AC5 ("a list that differs from the last one it logged ... SHALL get one note"), so the behaviour is defensible against the hard AC and deviates only from the soft invariant/comment. Non-blocking.
- **Task Requirement:** design Data Models: "`none` follows only a logged non-empty list" (R4 AC5)
