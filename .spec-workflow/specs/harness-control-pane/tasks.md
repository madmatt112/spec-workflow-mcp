## Decisions taken in this document

- D1 — The in-flight race loser gets a 409 through a new admission step: admission also refuses while a launch is in flight, the launch route calls admission, the setup-file write and the launch with no await between them, and the launcher's own in-flight check throws a launch error whose step is the new admission value, which the route maps to 409 run-live with no run id; the loser deletes no file. Options were a new admission step mapped to 409, a separate busy error class, a 500 carrying a step; chosen because the loser met a live launch, which requirement 3.8 answers with 409, and one error type keeps one catch in the route.
- D2 — The HANDOFF and gate parsers land in their own early task in the project-watch module: options were an early parser task, a stub in the run-setup module bridged later; chosen because the setup view needs the routing parser before the watch class can exist, and an early task needs no bridge.
- D3 — The launcher is two tasks, launch and admission first, then stop, finalise, own exit and restore: options were two tasks, one task; chosen because one prompt would carry every launcher behaviour and its whole test matrix at once.
- D4 — The fake CLI reaches the server through an optional harness field on the dashboard options: options were a server option, an environment variable naming the binary; chosen because an environment variable would let any inherited environment swap the spawned binary in production.
- D5 — The setup-file write and delete use synchronous file calls: options were synchronous, asynchronous; chosen because the launch route needs the admission, the write and the in-flight check in one event-loop turn (D1).
- D6 — During a stop the poll checks only that the process group exists, after one command-line check before the first signal: options were group-only polling after one command-line check, the full liveness check on every poll; chosen because requirement 3.9 names the group, and a group whose leader exited still holds its other members.
- D7 — The worker-override launch line goes only into the supervisor skill's launch prompt block: options were the supervisor skill only, adding a launch prompt block to the formats reference; chosen because the formats reference holds no launch prompt block today, so the design's launch-prompt-block edit can only mean the skill's block.
- D8 — The Harness page calls the harness routes with fetch directly: options were direct fetch, changing the shared PUT helper; chosen because the shared helper drops the error body on a non-ok response and other pages depend on it.
- D9 — The overview watch creates the state home's sdd directory before it watches: options were create the directory, poll for it, watch the whole state home; chosen because a chokidar 3.6.0 probe (node v24.13.0, 2026-09-28, scratch run) showed that a watched file reports add, change, unlink and add when its parent exists and nothing when the parent was missing at watch time, and the supervisor creates that directory anyway.
- D10 — The project watch owns the log re-point on a new launch; the hub's launch-update handler refreshes only the overview: options were the project watch, the hub; chosen because one owner of the log offset cannot reset it twice.
- D11 — The evidence file carries the seven decomposition steps as pending and three harness-check lines that the last task marks passed after it runs them: options were ten lines, seven lines with the checks only in task reports; chosen because the design's Testing Strategy makes each harness check a line of the evidence file.
- D12 — The hub exposes two read-only accessors for tests, the watched projects and whether the overview is active: options were accessors, inferring from message silence; chosen because silence cannot prove a watcher closed.
- D13 — A stop on a record already stopping returns the pending stop: options were return the pending stop, restart the stop; chosen because requirement 3.10 makes a re-pressed Stop safe.
- D14 — A drift test asserts that the setup module's eligible roles and DeepSeek models equal the provider script's lists: options were a drift test, reading the script at runtime; chosen because the script stays the one validator source and the test catches drift.
