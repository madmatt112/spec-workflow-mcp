## Summary

10.1-10.5 and NFR Security met, but an unreadable pushed.json is not treated as absent (startup pushes every open wait, defeating D3), and pushed.json is written non-atomically contrary to NFR Reliability.

## Findings

### CRITICAL: Unreadable pushed.json triggers a push burst instead of the baseline no-push path
- **File:** src/advisor/push.ts:149
- **Issue:** runStartupScan decides the first-start branch on fileExists(pushedPath()), i.e. existence, not readability. A present-but-corrupt pushed.json makes hadPushedFile=true, so it takes the 'push each open wait not recorded' branch; readPushedIds() returns an empty Set on the parse error, so every open wait is pushed. Design Error Handling scenario 8 (design.md:169) requires 'An unreadable pushed.json is treated as absent (baseline, no push)' and the task restriction states 'an unreadable pushed.json counts as absent'. This defeats D3's guarantee that a (re)start never bursts pushes for old waits (the realistic trigger is a torn write, enabled by the non-atomic write below). Untested: push.test.ts 'restart' uses a valid pushed.json. Fix: branch on a successfully-parsed pushed.json, not on fileExists.
- **Task Requirement:** Restriction: an unreadable pushed.json counts as absent; design Error Handling 8 (baseline, no push); D3

### WARNING: pushed.json written with fs.writeFile, not writeJsonAtomic
- **File:** src/advisor/push.ts:102
- **Issue:** writePushedIds writes via fs.writeFile, so a crash mid-write can leave a torn pushed.json. NFR Reliability (requirements.md:167) requires the 'pushed-id list' be written atomically via writeJsonAtomic (src/controller/state.ts:297-303). pushed.json has a single writer (the lock-holding pusher), so writeJsonAtomic applies cleanly. The non-atomic write is also the realistic trigger for the torn-file burst in the critical finding above.
- **Task Requirement:** NFR Reliability: pushed-id list written atomically (writeJsonAtomic)
