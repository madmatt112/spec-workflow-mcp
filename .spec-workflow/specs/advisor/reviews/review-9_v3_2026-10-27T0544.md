## Findings

### WARNING: Synchronous embed path rejects instead of meaning:off on mid-refresh embedder failure (Error Handling #7)
- **File:** src/advisor/search/index.ts:226
- **Issue:** Design Error Handling #7 (design.md:168): 'Embedder unreachable mid-refresh: refresh stops, the index keeps what it wrote, result says meaning: off.' Fix round 2 wrapped ONLY the >200-chunk background path (embedDeferred, index.ts:170-198). The synchronous path — the COMMON path for any corpus with <=200 chunks to embed — is still unguarded: the <=200 corpus-embed loop at index.ts:221-232 calls embedder.embed() with no try/catch, and the query embed at search.ts:87 (await embedder.embed([q.query])) is also unguarded. loadEmbedder only pings at t0 (embed.ts:54); embed() throws on any non-2xx (embed.ts:44) and fetch rejects on a dropped connection, both routine mid-request (Ollama 5xx under load). So a mid-refresh failure makes refreshIndex/run reject and search() return a rejected promise to the caller instead of text hits with meaning:'off', directly contradicting an explicit enumerated design clause on the main path. v2's WARNING asked for 'the background (and synchronous) embed' to be wrapped; only the background half was done, so this is recurring. No test covers synchronous-path degradation (the folded crash test search.test.ts:548-574 exercises the >200 background path only). Fix: wrap the synchronous corpus-embed loop and the query embed in try/catch; on failure stop, keep what was written, and return meaning:'off' with the text hits, plus a test for a <=200-chunk corpus whose embedder fails mid-embed.
