Scenario 1: a live-driven run and a seeded waiting run both carry the deploy hold; the live drive parks paused/operator at its next stop point; a controller restart (DeployUnit spawned detached with its own process group, pid+startTime persisted to a file so a fresh DeployUnit instance finds the same child) leaves the live unit alone; releasing a prestart gate lets the script finish to done with commit; holds release; the paused run resumes from its cursor through reviewer/implementation/retro to the retro-plan wait; the waiting run stays waiting. Scenario 3: a failing eval gate (stub cli exits 1) leaves failed with error starting "gate:", writes the self-update error wait via a stubbed dist/controller/waits.js, leaves the live checkout's old dist/ untouched, and releases two held runs. Scenario 5: (a) a controller stopped while the record is at wait with the unit alive (via a prestart gate) leaves the unit running and a new controller finishes the record to done; (b) with deployDisabled on the first controller (so its own tick never starts the unit), a restart with unitStarted unset starts a fresh unit and finishes to done. Scenario 6: with deployDisabled and the unit started by hand, SIGKILLing the child at build leaves the record at build (no trap runs); a controller restart's onStart finds the unit gone and writes failed, releasing the hold.
