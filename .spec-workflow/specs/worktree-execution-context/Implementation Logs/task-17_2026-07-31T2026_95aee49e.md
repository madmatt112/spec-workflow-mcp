- **Description:** src/tools/__tests__/projectPath.test.ts — new describe 'workflow root and workspace path that differ'. THE GAP THIS CLOSES: every case above it builds `{ projectPath: X, workspacePath: X }`, so a tool reading the wrong root still lands on the right directory and no assertion can fail. The new block creates two temp dirs (main-checkout / worktree) and gives each a decoy the other lacks, so the directory a tool reaches is observable. Six cases: (1) spec-status with no override finds `workflow-only-spec` and reports `workspace-only-spec` not found; (2) spec-status with `projectPath: <workspace>` finds `workspace-only-spec` — spec-status is deliberately NOT one of requirement 3.8's four selectRoots tools, so its override is taken verbatim and NOT re-derived; (3) log-implementation with no override writes into `<workflowRoot>/.spec-workflow/specs/log-spec/Implementation Logs` while the identically-seeded workspace copy never gets a log directory; (4) log-implementation with `projectPath: <workspace>` sends the log to the override and leaves the context workflow root's copy empty — the temp workspace is not a git repo so selectRoots degrades to verbatim, which is fine here because the assertion is about the CONTEXT root no longer being used; (5) approvals with no override reads the workflow root's MDX-hostile requirements.md and fails the MDX gate; (6) the same call with `projectPath: <workspace>` reads the workspace's clean copy and does not. Cases 5/6 use the same relative filePath under both roots with different content, which is what makes them two-way discriminating. Teardown is an explicit afterAll (rm of the temp root + _resetRootSelection); console.warn is spied to silence selectRoots' override warning, whose text task 14 already asserts.
