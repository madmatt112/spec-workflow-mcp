#### callToolFromWorktree
- **Purpose:** Calls ONE MCP tool on a server spawned exactly the way the harness spawns its own (node <tsx cli> <absolute entry> <main checkout>, cwd = the worktree), using the MCP SDK's Client + StdioClientTransport. This is what makes 'a review triggered from worktree A' literal rather than simulated: the only input distinguishing A from B is where the child was standing, so the tool runs under the INFERRED context. A dedicated short-lived server is used rather than the harness's long-lived children because those have no client attached and a tool call needs the initialize handshake; it registers as a second instance of the same project, which changes no project count. stderr is piped AND drained (an unread pipe fills and blocks the child). #### stripMethodology
- **Purpose:** DEFECT WORKAROUND, documented at the call site. toMCPResponse encodes the whole ToolResponse with @toon-format/toon, and for BOTH tools called here the `methodology` value is a multi-thousand-character markdown blob that the SAME library re-encodes into a document its own decode() rejects with 'Expected 0 inline array items, but got 1'. Verified by round-tripping the real methodology string in isolation: encode({methodology: <string>}) then decode() throws. With this one line filtered out the document decodes and every other field survives intact (diff, diffStats, fileResolution, filesToReview, targetFile). Safe as a line filter because TOON puts every value on one physical line - embedded newlines are \n escapes - so no quoted value can span or hide one of these lines.
- **Location:** e2e/worktree-shared.spec.ts:77
- **Signature:** stripMethodology(toon: string): string
- **Exported:** No

- **Purpose:** Gives one worktree a committed base and then an uncommitted edit to it, via HarnessWorktree.writeFile/commitAll. #### waitForRegistrationAttempts
- **Purpose:** Waits until every named server has FINISHED its registration attempt, matching /Project (NOT )?registered/ in the harness's captured logs (the NOT branch is requirement 6.4's continue-unregistered path). Gating on the log rather than on the registry is what makes a lost update fail fast and unambiguously: server.ts prints that line only after reading its own entry back, so once both have printed, both writes are done - a registry still short an entry at that point has LOST one, it is not merely slow. Polling the registry instead would make every lost update look like a 60s timeout.
- **Location:** e2e/worktree-shared.spec.ts:508
