# Adversarial Analysis — worktree-execution-context/requirements (v2)

Phase: requirements. Attack surface: completeness, ambiguity, scope.

All line citations below were re-checked against the working tree at review time. Every citation the target document makes was also verified; they are accurate.

v1 landed. The document now names both roots, requires `workspacePath`, reverses the borrowed compiler, kills the `.mcp.json = .` recommendation, and puts ownership, diff base, concurrency, and a test fixture in scope. The findings below are what the *fixes* created or left open.

---

## 1. The out-of-scope declaration is now load-bearing and false — Requirement 1 multiplies dashboard projects onto one shared root

**Novel.** The Introduction says: "Deliberately out of scope: repo grouping in the dashboard UI and per-worktree badges… Once identity is correct, the existing `repo · worktree` naming is sufficient at the scale this addresses." Naming is not the problem. Content duplication is.

`addProject` builds every per-project component from the **workflow root**, not the workspace: `new SpecParser(translatedWorkflowRootPath)`, `new SpecWatcher(translatedWorkflowRootPath, parser)`, `new ApprovalStorage(translatedWorkflowRootPath, …)`, `new SpecArchiveService(translatedWorkflowRootPath)` (`src/dashboard/project-manager.ts:146-152`). Today N worktrees collapse to one `projectId`, so this happens once. After Requirement 1, N worktrees are N registry entries with N `ProjectContext` objects — all four components instantiated N times against the same `<main>/.spec-workflow`.

- **Confront the consequence the exclusion waves away.** Three worktrees produce three dashboard projects — `repo`, `repo · wt-a`, `repo · wt-b` — each listing *every* spec, *every* approval, and *every* task, because they read one directory. The user does not see "one entry per worktree"; they see the entire project three times. Requirement 1's own user story ("the dashboard … know where the agent actually is") is satisfied only in the project name; the payload underneath is triplicated. Either dedupe the shared views or stop claiming naming suffices.
- **Attack the interaction with Requirement 4 AC 5 directly.** With N duplicate entries, the user clicks "review task 3.2" from whichever project row they happen to see. R4 AC 5 then fires a workspace mismatch for N−1 of the N rows — so after this spec ships, the *majority* of dashboard-triggered reviews report a mismatch. The document never says what "report it" does: refuse, run with an empty `filesToReview`, or run anyway with a warning. An empty file set that still produces a verdict is the failure this spec is named after, wearing a disclosure.
- **Cost the scheduled cleanup loop.** `JobScheduler.executeJob` iterates `getProjectsList()` and calls `cleanupSpecs(projectContext.parser, projectContext.projectPath, …)` for each (`src/dashboard/job-scheduler.ts:161-190`), which does `fs.rm(join(projectPath, '.spec-workflow', 'specs', spec.name), { recursive: true, force: true })` (`:259`). R6 AC 10 correctly keeps that on the workflow root — and thereby guarantees N sequential recursive deletes against **one** directory per scheduled run, with `itemsDeleted` inflated N×. `cleanupApprovals` has the same shape via N `ApprovalStorage` instances on one approvals dir. R6 AC 10's rationale stops at "don't point it at the worktree" and never asks what happens when N projects share one target.
- **Count the watchers.** N `SpecWatcher` instances on the same tree means every `tasks.md` save fans out to N `spec-change` events and N SSE broadcasts, each tagged with a different `projectId` (`src/dashboard/project-manager.ts:159-176`). The Performance NFR budgets startup git calls to the millisecond and says nothing about this.
- **Force the scope decision.** Either dedupe by `workflowRootPath` in the dashboard (grouping — currently excluded), or state in the Introduction that N worktrees produce N full copies of the project view and that this is accepted. The current text asserts the opposite.

## 2. Requirement 5 — the diff base was decided without bounding what it changes

**Compounding** (v1 demanded a decision; v2 made one and left its blast radius unexamined).

- **Reverse AC 6's parity claim; it is false for the common case.** AC 6 promises identical file sets "on the default branch itself in a non-worktree project." AC 2 resolves the default branch first via `git symbolic-ref refs/remotes/origin/HEAD` — a *remote-tracking* ref. A developer sitting on local `main` with three unpushed commits gets `merge-base(HEAD, origin/main) ≠ HEAD`, so the diff now spans those three commits where `git diff HEAD` (`src/core/task-diff.ts:45-46`) showed only the working tree. This repo's own history is exactly that pattern. AC 6 as written is contradicted by AC 2 as written.
- **Bound the diff to the task, or admit it no longer is one.** `computeTaskDiff` is called with `validatedAllFiles` as pathspec — the files from *this task's* implementation log (`src/tools/review-task.ts:361`, `:389`). Against `HEAD` that yields "what is uncommitted in those files." Against a merge-base it yields "everything that happened to those files on this branch." Task 5 touching `multi-server.ts` now shows task 1's and task 3's committed edits to the same file as part of task 5's review. The reviewing agent is told this is the task's work and will grade it. No AC scopes the diff back to the task, and no AC discloses the overlap.
- **Handle the stale-remote case.** Nothing fetches. `origin/main` in a two-week-old clone puts the merge-base two weeks back, so the review diff absorbs every upstream change to those files since. Specify a freshness expectation or state that the base is whatever is locally known.
- **Resolve AC 2's ref-type inconsistency.** Step 1 yields a remote-tracking ref, step 2 yields a bare branch *name* from `init.defaultBranch` (which is usually unset — it is not a fallback, it is a coin flip), step 3 yields a local ref. Merge-base against a stale local `main` and against a fetched `origin/main` are different commits. The precedence list picks between incommensurable things without saying how a name becomes a ref.
- **Scope-check the requirement itself.** R5 changes review behaviour for **every user on a feature branch**, worktree or not, delivered inside a spec titled "worktree-execution-context," with no setting and no opt-out. That is the largest behavioural change in the document and the only one with no non-worktree escape. Either gate it behind the same kind of flag R1 got (`--no-workspace-inference`) or move it to its own spec.

## 3. Requirement 9 — the `tasks.md` ACs govern a writer that does not race; the writer that does is outside this codebase

**Compounding on v1, and the fix missed.** v1 said "add the write that actually races: `tasks.md`." v2 added AC 5 and AC 6: "the writer SHALL re-read the file immediately before writing, apply only its own status-marker change, and write atomically."

There is exactly one `tasks.md` writer in the repository: the dashboard's task-status endpoint (`src/dashboard/multi-server.ts:1425-1452`, via `updateTaskStatus` at `src/core/task-parser.ts:342`). It is single-process. It is not the racing writer.

- **Name the actual writer.** `spec-workflow-guide.ts:281` instructs agents: "**Direct editing**: Mark tasks as in-progress [-] or complete [x] in tasks.md." `review-task.ts:525`, `:537`, `get-task-review.ts:133-134`, `log-implementation.ts:399`, and `spec-status.ts:119` all end with "Edit tasks.md: change [-] to [x]." There is no MCP tool that sets task status. Two agents in two worktrees mutate the shared `<main>/.spec-workflow/specs/x/tasks.md` with their own editor tools; this server never sees the write and cannot re-read, merge, or retry it.
- **Declare R9's user story unmet.** "Parallel work does not silently lose data" is precisely the guarantee AC 5/6 cannot deliver for the file most likely to lose it. Implement AC 5/6 exactly and the dashboard endpoint becomes safe against a race it was never in, while the real one is untouched — and the requirement will be marked done.
- **Force the choice.** Either (a) add a task-status MCP tool and change the guide to route status changes through it (a real scope addition this document has not costed), or (b) state plainly that concurrent agent edits to a shared `tasks.md` are unprotected and out of scope, and delete AC 5/6's implication otherwise. Do not ship the current wording, which reads as protection.
- **Extend AC 1/AC 3 to the other registry writers.** AC 1 and AC 2 name registration. `cleanupStaleProjects` (`src/core/project-registry.ts:297-320`) is a second unlocked read-modify-write that *deletes* entries, and it runs against a snapshot. A cleanup pass that reads before a new worktree registers and writes after will drop that registration. AC 3's generic "concurrent modification detected between read and write" is the right shape but is attached to the write path only.
- **Define exhaustion.** AC 6 says a `tasks.md` retry that exhausts "SHALL surface an error." AC 3 says the registry write retries "up to a bounded number of attempts" and stops there. What happens on exhaustion — does the MCP server start unregistered and invisible to the dashboard, or abort? Undefined. The Reliability NFR's fail-closed rule covers git invocations only.

## 4. Requirement 7 — the honesty gate still cannot detect the dishonest case, and AC 6 + AC 7 leave the cache untracked

**Recurring (escalate) and Novel.**

- **AC 3 is unimplementable as written — escalate it.** "WHEN a typecheck cannot run for any reason THEN neither the absence nor the presence of diagnostics SHALL be presented as a completed typecheck." The only detector any AC supplies is AC 1: the *binary* is missing. Concretely: `git worktree add` at time T, `npm ci`, branch adds a `zod` dependency, agent implements the task. `<worktree>/node_modules/.bin/tsc` exists, so AC 1 does not fire (`src/core/typecheck.ts:134-136`, `:361-374`). `tsc` runs, cannot resolve `zod`, exits non-zero with a wall of `TS2307`, and `runProjectTypecheck` returns `status: 'success'` because the only non-success paths are timeout, overflow, and unparseable output (`:157-191`). v1 raised this against the borrowed compiler; removing borrowing did not remove it — a worktree's own stale or partial `node_modules` produces the same flood. Add a detector (e.g. treat a run whose diagnostics are overwhelmingly `TS2307`/`TS2688` as `unavailable`) or drop AC 3's promise.
- **Attack AC 6 and AC 7 as a pair; they do not compose.** AC 6 puts the cache at `<workspace>/.spec-workflow/.cache` and AC 7 sends `ensureGitignoreEntry` to the **workflow root**. `.gitignore` is a tracked file: each worktree checks out its own copy from its own branch. Appending to `<main>/.gitignore` in the main checkout's working tree has no effect whatsoever on what git ignores inside `<worktree>` until that edit is committed and the worktree's branch contains it. Result: every worktree acquires an untracked `.spec-workflow/.cache/tsc.tsbuildinfo` that shows in `git status` and is a candidate for an agent's `git add -A`. AC 7's stated harm ("an uncommitted modification in every worktree") is not avoided either — it is relocated to the main checkout, where the main project's own review diff picks it up.
- **Name the mechanism that actually works.** `$(git rev-parse --git-common-dir)/info/exclude` is untracked, shared across all worktrees, and needs no commit. Specify that, or specify that the cache is written outside the repo entirely (e.g. under `tmpdir()` keyed by workspace hash). Either beats a tracked file that cannot reach the directory it is supposed to cover.
- **Note what makes this survivable today and why that is not a defence.** This repo's tracked `.gitignore:148` already contains `.spec-workflow`, and `ensureGitignoreEntry` treats that as covered and returns (`src/core/typecheck.ts:391-397`). So the defect is invisible in the repo where it will be developed and tested, and visible only in user repos whose committed `.gitignore` lacks the entry. R10 must force the fixture to construct the uncovered case.
- **Challenge AC 1's reason string as a claim the check cannot support.** `resolveTscBinary` tests one path: `<projectPath>/node_modules/.bin/tsc` (`:362-374`). "No binary" does not mean "worktree dependencies missing" — it also means production-only install, pnpm layout, or a project that never had TypeScript locally. AC 2 makes the *reason* a function of whether the two roots differ rather than of the observed cause, so the string asserts a diagnosis the code never made.

## 5. Requirements 3 and 4 — the disclosures never reach the reviewing agent, and containment silently eats spec files

**Novel.**

- **R3 AC 6 fixes a payload the runner throws away.** AC 6 requires `handlePrepare`'s `projectContext` to disclose both roots (`src/tools/review-task.ts:430-435`). `TaskReviewRunner.executeJob` destructures exactly five fields from the response — `const { taskContext, implementationSummary, steeringExcerpt, filesToReview, methodology } = prepareResponse.data;` (`src/dashboard/task-review-runner.ts:110`) — and `buildPrompt` (`:138`) is built from those. `projectContext` is discarded. The disclosure therefore reaches an agent calling `review-task` directly and never reaches the dashboard-spawned reviewer, which is the route the Introduction opens with. Add an AC on `buildPrompt`, or AC 6 is decorative on the primary path.
- **Same defect, R5 AC 5.** "The review output SHALL state which base was used" — via which field, surfaced by whom? `TaskDiffResult` (`src/core/task-diff.ts:4-10`) has no slot for it, and even if one is added, the runner's prompt does not carry it. R5 AC 3's "indicator that the fallback occurred" has the same problem. Two ACs require disclosure and no AC names the disclosure channel.
- **Attack R4 AC 3/AC 4 as a silent data-loss path.** `validateAllFiles` resolves each logged path against the containment root and drops it with **no warning at all** when `safeRealpath` returns undefined (`src/tools/review-task.ts:63-67`; the `warnOnce` at `:72-76` covers only the outside-root case). Move the root to the workspace and every logged `.spec-workflow/specs/…/design.md` — which agents routinely record in `filesCreated` — resolves to a path that does not exist inside the worktree and vanishes from `filesToReview` silently. A documentation or spec-authoring task reviewed from a worktree gets an empty file set and a verdict anyway. Specify two-root resolution (workspace first, workflow root fallback) or explicitly exclude `.spec-workflow` paths with a stated reason.
- **Reverse R3 AC 4's default.** "WHEN a tool accepts an `args.projectPath` override … the tool SHALL derive the workspace path from the override." Every affected tool already does `args.projectPath || context.projectPath` (`src/tools/review-task.ts:276`, `src/tools/log-implementation.ts:307`, `src/tools/adversarial-review.ts:51`), and `projectPath` is an exposed tool argument agents pass habitually. Deriving the workspace from the override means `resolveGitWorkspaceRoot(<main repo>)` → the main checkout: an agent in a worktree that passes `projectPath` explicitly gets the pre-fix behaviour back, silently, with `context.workspacePath` sitting right there unused. R3 AC 1 rejected exactly this shape of silent fallback one criterion earlier. At minimum require a log line, and require R10 to cover it — currently no AC in R10 does.
- **State the containment consequence for the nested-worktree layout.** When worktrees live under the main repo (`~/repo/worktrees/a`), the workspace is a *descendant* of the workflow root, so `.spec-workflow` sits above the containment root and R4 AC 3's guard rejects it. The Security NFR's "SHALL NOT widen to any ancestor" covers the reverse direction only.

## 6. Requirements 1, 2 and 8 — plumbing gaps in the new resolution path

**Novel.**

- **`--no-workspace-inference` will be swallowed by the argument filter.** `parseArguments` strips flags via an explicit denylist — `--dashboard`, `--port=`, `--port`, `--no-open`, `--no-shared-worktree-specs` (`src/index.ts:166-175`) — and takes `filteredArgs[0]` as the project path (`:178`). R1 AC 10 introduces a flag and never says to add it to that list. Pass it alone and `rawProjectPath` becomes the literal string `--no-workspace-inference`; `resolveGitWorkspaceRoot` throws internally and returns the string unchanged (`src/core/git-utils.ts:18-28`), and the server registers a project whose path is a flag. Pass it before the path and the path is ignored. The AC must name the filter.
- **AC 2 AC 6 scrubs one environment variable and leaves its twin.** `SPEC_WORKFLOW_SHARED_ROOT` is inherited by every spawned agent through `env: { ...process.env }` (`src/dashboard/task-review-runner.ts:368`, `src/dashboard/adversarial-runner.ts:145`) and short-circuits `resolveGitRoot` before any git call (`src/core/git-utils.ts:37-41`), relocating the child's **workflow root** exactly as `SPEC_WORKFLOW_WORKSPACE` would relocate its workspace. R1 AC 5 already acknowledges this variable can lie; the spawn boundary needs the same treatment for both, plus a stated position on `SPEC_WORKFLOW_HOST_PATH_PREFIX`/`_CONTAINER_PATH_PREFIX`, which make `isProcessAlive` return `true` unconditionally (`src/core/project-registry.ts:164-171`) and are inherited by the same spawns.
- **Contradiction between the "single source of truth" NFR and R1 AC 9.** The NFR says "workspace resolution lives in one exported function in `src/core/git-utils.ts`. `src/index.ts` calls it; **no other module** re-derives the workspace path from git." `ProjectManager.addProjectByPath` re-derives it right now — `resolveGitWorkspaceRoot(projectPath)` then `resolveGitRoot(workspacePath)` (`src/dashboard/project-manager.ts:264-265`) — and R1 AC 9 plus R2 AC 5 deliberately exclude dashboard mode from the new resolution. So the NFR is violated by code the requirements exempt from change. Worse, that path also skips R1 AC 7's `realpath` normalization, so a manually added symlinked worktree still produces a duplicate `projectId` under `generateProjectId` (`src/core/project-registry.ts:29-33`). Either extend AC 7 to the manual-add path or scope the NFR honestly.
- **R8 AC 3 leaves the migration state undefined.** Pre-change log entries carry no workspace path; AC 3 says treat it as "unknown" and do not assume it matches. R4 AC 5 defines behaviour for a *mismatch*. Unknown is neither match nor mismatch. Every task logged before upgrade is in that state — so on day one after release, every review of existing work hits an unspecified branch. Say whether unknown proceeds silently, proceeds with a disclosure, or is treated as a mismatch, and add it to the Migration NFR.
- **R8 AC 1 records a derived value, not an observed one.** `log-implementation` reads `args.projectPath || context.projectPath` (`src/tools/log-implementation.ts:307`); under R3 AC 4 an override redirects the recorded workspace too. The field then records "the workspace implied by the argument the agent passed," which is precisely the value R4 AC 5 is supposed to cross-check against. A mismatch detector whose source of truth is corruptible by the same override it is checking is not a detector.

## 7. What is actually fine

- R6 AC 10 (cleanup stays on the workflow root) is the correct reversal of v1's finding; only the N× loop consequence in §1 remains.
- R9 AC 8 correctly marks the approval workspace-first resolution as already implemented (`src/dashboard/approval-storage.ts`, wired at `src/dashboard/project-manager.ts:148-151`) rather than padding the count.
- The Security NFR's "realpath before containment, not only before hashing" is already satisfied in `validateAllFiles` (`src/tools/review-task.ts:49`); state it as a non-regression, as R9 AC 8 does.
- The Introduction's reframing of both dashboard routes as independently wrong is accurate, and every line citation in the document checks out.

## Top 5 risks and gaps

1. **The identity fix triplicates the dashboard, and the out-of-scope note denies it.** N worktrees become N projects whose parser, watcher, approval storage, and archive service all point at one `.spec-workflow` (`src/dashboard/project-manager.ts:146-152`). Every spec, approval, and task appears N times; scheduled cleanup runs N recursive deletes over one directory (`src/dashboard/job-scheduler.ts:161-190`, `:259`); R4 AC 5 fires a mismatch on N−1 of N rows. "Repo grouping is out of scope because naming suffices" is the one claim in the document that the code contradicts outright.
2. **Requirement 9's `tasks.md` criteria protect the wrong writer.** The only in-repo writer is the single-process dashboard endpoint (`src/dashboard/multi-server.ts:1452`). Every agent changes task status by editing the file directly, as the guide instructs (`src/tools/spec-workflow-guide.ts:281`). AC 5/6 are implementable and will not prevent a single real loss.
3. **Requirement 5 changes review scope for all users and its own parity criterion is false.** `merge-base(HEAD, origin/main)` ≠ `HEAD` for anyone with unpushed commits on the default branch, contradicting AC 6; on a branch, a task's diff now includes every earlier task's committed edits to the same files.
4. **Requirement 7 AC 3 has no detector.** A worktree with a stale `node_modules` runs `tsc`, floods `TS2307`, and returns `status: 'success'` (`src/core/typecheck.ts:157-191`). AC 1 gates only on a missing binary. This is v1's finding surviving a fix that addressed a different cause — escalate.
5. **AC 6 + AC 7 leave the typecheck cache untracked-and-unignored in every worktree,** because `.gitignore` is a tracked per-worktree file and the entry is written to the main checkout's copy. Invisible in this repo, whose `.gitignore` already covers `.spec-workflow`.

## Top 3 conclusions to challenge or reverse

1. **"Repo grouping in the dashboard UI is deliberately out of scope; `repo · worktree` naming is sufficient." Reverse it, or restate the cost.** Correct identity plus a shared workflow root equals N complete copies of the project view, N cleanup passes over one directory, and a mismatch warning on most dashboard reviews. Either dedupe shared views by `workflowRootPath` — which is grouping — or replace the sentence with an explicit statement that N worktrees produce N full duplicates and that this is accepted.
2. **"Requirement 9 makes concurrent worktrees safe." Reverse the `tasks.md` half.** Nothing in this codebase writes task status on an agent's behalf. Either add a status-setting MCP tool and reroute the guide (real, uncosted scope), or delete AC 5/6 and state the limitation. Shipping ACs that describe a protection the architecture cannot provide is how the requirement gets marked done while the data loss continues.
3. **"Requirement 5 belongs in this spec." Split it, or gate it.** It is the only requirement that changes behaviour for users who have never opened a worktree, it has no opt-out where R1 got one, its parity criterion is false as written, and it silently widens a per-task diff into a per-branch diff. Diff-base selection is a separate spec with its own parity and disclosure work.

## What's missing — do this before acting on the document

- **A dashboard-duplication decision.** Specify what the dashboard does when N projects share one `workflowRootPath`: group them, hide shared views on non-primary entries, or accept duplication and say so. Everything in §1 follows from this one unanswered question.
- **A named disclosure channel.** One requirement stating which fields (`workspacePath`, `workflowRoot`, `diffBase`, fallback indicator, typecheck `reason`) reach the reviewing agent, and that `TaskReviewRunner.buildPrompt` (`src/dashboard/task-review-runner.ts:110`, `:138`) carries them. Three ACs currently require disclosure into a payload the runner discards.
- **A defined outcome for "unknown workspace" and for detected mismatch.** R4 AC 5 and R8 AC 3 both stop at "report." Say whether the review proceeds, proceeds with a warning, or refuses — and cover the pre-upgrade backlog in the Migration NFR.
- **A dependency-resolution detector for the typecheck,** or an explicit retraction of R7 AC 3. Binary presence is not runnability.
- **The ignore mechanism for the worktree cache** — `$GIT_COMMON_DIR/info/exclude`, or move the cache out of the repo. And an R10 fixture whose test repo has *no* `.spec-workflow` entry in its committed `.gitignore`, so the case is reachable in test.
- **Argument-parsing detail for `--no-workspace-inference`** (add to the filter at `src/index.ts:166-175`) and env scrubbing for `SPEC_WORKFLOW_SHARED_ROOT` alongside `SPEC_WORKFLOW_WORKSPACE` at both spawn sites.
- **R10 coverage for the criteria that carry the most new risk:** R2 AC 6 (env scrubbing), R3 AC 4 (`args.projectPath` override), R4 AC 5 (mismatch), R6 (two-field runner contract), R8 (attribution round-trip), and the Reliability NFR's removed-worktree case. R10 currently verifies R1, R2 overrides, R3 AC 7, R5 AC 6, R7, and R9 AC 2 — the parity and degradation criteria — and none of the new behaviour introduced by the fixes.
