# Adversarial Analysis — worktree-execution-context/requirements (v1)

Phase: requirements. Attack surface: completeness, ambiguity, scope.

All line citations below were checked against the working tree at the time of review.

---

## 1. Requirement 5 — "pass the project's workspace path as the runner's project path"

This requirement assumes the runners have a slot for a workspace path. They do not. `TaskReviewRunner.RunOptions` (`src/dashboard/task-review-runner.ts:27-35`) has exactly one path field, `projectPath`, and `executeJob` spends it three ways that this spec says must now diverge:

- `PathUtils.getSpecPath(opts.projectPath, opts.specName)` (`:95`) — must stay on the shared workflow root.
- `const context: ToolContext = { projectPath: opts.projectPath }` (`:100`) — feeds `reviewTaskHandler`, which needs both roots.
- `this.runAgent(jobId, opts.projectPath, ...)` (`:144`) → `spawn(cli, args, { cwd })` (`:365`) — must be the worktree.

Directives:

- **Challenge AC 5.1 and 5.2 as written.** "SHALL pass the project's workspace path as the runner's project path" is a literal instruction to set `RunOptions.projectPath = project.workspacePath`. Implement it exactly and `getSpecPath` resolves `<worktree>/.spec-workflow/specs/<name>`, which does not exist — `handlePrepare` returns `tasks.md not found for spec '<name>'` and every dashboard-triggered task review in a worktree fails outright. The spec replaces a wrong-checkout review with no review at all.
- **Resolve the direct contradiction between AC 5.1 and AC 5.5.** AC 5.5 says settings "SHALL continue to load from the shared workflow root." `loadSettings` is called on `project.projectPath` at the route (`src/dashboard/multi-server.ts:1776`, `:1828`) — fine — but `TaskReviewManager(specPath)` inside the runner (`:96`) derives from the same single field AC 5.1 redirects. Two ACs govern one variable and demand different values. Name the second field (`workspacePath` on `RunOptions`) or the requirement is unimplementable as stated.
- **Correct AC 5.4 — the cited lines are not runner spawns.** `src/dashboard/job-scheduler.ts:178` and `:186` are `projectContext.projectPath` arguments to `cleanupSpecs` and `cleanupArchivedSpecs`, which resolve `join(projectPath, '.spec-workflow', 'specs', ...)` (`:259`) and `join(projectPath, '.spec-workflow', 'archive', 'specs', ...)` (`:290`) and **delete directories**. The job scheduler spawns no agent. Implementing AC 5.4 literally points a destructive cleanup at the worktree, where it either silently finds nothing (cleanup quietly stops working for every project) or operates on a stray `.spec-workflow` that Requirement 6 AC 5 will have just created there. This AC contradicts AC 5.5 and R7 AC 3 and must be deleted or rewritten as "SHALL continue to use the workflow root."
- **Close the gap at `multi-server.ts:828`, three lines above the cited `:851`.** The same request handler calls `adversarialReviewHandler(..., { projectPath: project.originalProjectPath })`, and that handler does `PathUtils.getWorkflowRoot(projectPath)` (`src/tools/adversarial-review.ts:60`). `originalProjectPath` is the *workspace* path (`src/dashboard/project-manager.ts:183`), so in a worktree the handler already looks for `.spec-workflow` inside the worktree and fails to find the target document. AC 5.3 fixes only the runner call below it. Ship this spec as written and dashboard adversarial review stays broken in exactly the scenario the spec exists for.
- **Stress-test AC 5.6 against the child's own MCP server.** Setting the child's cwd to the worktree only helps if the child's `spec-workflow` server then resolves the worktree — which is Requirement 1's inference, running in a process the dashboard spawned with `env: { ...process.env }` (`task-review-runner.ts:368`). If the dashboard process has `SPEC_WORKFLOW_WORKSPACE` set (R2 AC 1), every spawned review agent inherits it and pins to one workspace regardless of cwd. No AC addresses env inheritance across the spawn boundary.

## 2. Requirement 3 — the "additive" context change is where the fix leaks out

- **Challenge AC 3.2's silent fallback.** "WHEN a tool reads `workspacePath` from a context that does not supply one THEN it SHALL fall back to `projectPath`" guarantees that any construction site not enumerated by this spec keeps the old, defective behaviour — silently, with no warning and no test that can catch it. `TaskReviewRunner` builds its `ToolContext` by hand at `task-review-runner.ts:100`; AC 3.1 covers only `src/server.ts:96`. Under the current AC set, the dashboard review path compiles, runs, falls back, and diffs the wrong checkout. The headline defect survives full implementation of Requirements 3 and 4.
- **Enumerate every `ToolContext` construction site, not just the server's.** The requirement's own NFR ("No existing tool is required to change") is what makes this dangerous: an optional field with a silent default is indistinguishable, at runtime, from the bug. Require either a non-optional field or a logged warning when the fallback fires.
- **Stress-test the interaction with `args.projectPath`.** Every affected tool starts with `const projectPath = args.projectPath || context.projectPath` (`src/tools/review-task.ts:276`, `src/tools/log-implementation.ts:308`, `src/tools/adversarial-review.ts:51`), and there is a dedicated test file for this input (`src/tools/__tests__/projectPath.test.ts`). There is no `args.workspacePath`. When a caller overrides `projectPath` to project B while `context.workspacePath` still holds project A's worktree, Requirement 4 will diff and typecheck A's code against B's spec — a *new* cross-project mismatch this spec introduces. No AC says what happens when the argument override is present.
- **Challenge AC 3.3 as untestable in its own terms.** "behaviour SHALL be identical to the behaviour before this change" names no observable. Identical in what — the file list, the diff bytes, the `tsconfigPath` string, the cache location? Requirement 6 AC 5 moves the cache directory unconditionally, so AC 3.3 and R6 AC 5 are already inconsistent for the non-worktree case where the two paths are equal but the cache root changes from workflow root to workspace path (the same value — state that, or the parity claim reads as false).
- **Require the returned `projectContext` to disclose both roots.** `handlePrepare` returns `projectContext: { projectPath, workflowRoot }` (`review-task.ts:430-435`) straight to the reviewing agent. After this change that object still advertises the shared root as "the project path" while `filesToReview` points into the worktree. Nothing in Requirement 4 updates the payload the agent actually reads.

## 3. Requirements 1 and 2 — identity inference inverts explicit-over-inferred, and AC 2.4 is false

- **Challenge the precedence in AC 2.3.** `SPEC_WORKFLOW_WORKSPACE` → cwd inference → configured path argument places an *incidental* signal (whatever directory the client happened to launch in) above an *explicit* one (the path the user typed into `.mcp.json`). Construct the failure: a user deliberately configures the worktree path but opens a terminal in `~/repo` and runs the agent there; AC 1.1 fires, both paths share a git common dir, and the server silently discards the explicit configuration. The doc never states this inversion as a decision or defends it.
- **Expose the circularity in the escape hatch.** Requirement 2's user story is "I am not dependent on inference being right," and the fix is a per-process env var. But Requirement 1's user story is "without my having to maintain a separate `.mcp.json` per worktree." A per-worktree `SPEC_WORKFLOW_WORKSPACE` is per-worktree configuration by another name. There is no way to say "trust my path argument, skip inference" using a config file that is, by the spec's own premise, tracked in git and identical in every worktree.
- **Reverse or repair AC 2.4.** It asserts `SPEC_WORKFLOW_WORKSPACE` "SHALL NOT affect the resolution of `workflowRootPath`." Read `src/index.ts:181`: `resolveGitRoot(workspacePath)` — the workspace path *is* the input. Set `SPEC_WORKFLOW_WORKSPACE=/home/me/other-repo` and `workflowRootPath` moves to that repo's root; add `--no-shared-worktree-specs` and `workflowRootPath` becomes the env var value verbatim. AC 2.4 is not a constraint, it is a factual claim about the current code, and it is wrong. Either require `resolveGitRoot` to run on the configured path instead (a behaviour change nobody has specified) or drop the claim.
- **Scope the env var to MCP-server mode.** AC 1.7 excludes dashboard mode from *inference*; Requirement 2 says nothing about mode. The dashboard is multi-project and re-derives paths itself at `src/dashboard/project-manager.ts:264-265`. One global env var in the dashboard's environment applied to `addProjectByPath` collapses every manually added project onto a single workspace path. Specify that Requirement 2 applies only where a project is registered from the CLI.
- **Add an AC for path spelling.** `projectId` is `sha1(absolutePath)` (`src/core/project-registry.ts:29-33`) over a raw string. `resolveGitWorkspaceRoot` returns git's own spelling; a user-supplied path may be a symlink or a differently-cased drive letter. R7 AC 1 promises each worktree gets "a distinct entry" but nothing promises each worktree gets *exactly one*. On macOS (`/tmp` → `/private/tmp`) or with symlinked checkouts, the same worktree registers twice and the dashboard shows phantom duplicates. Require realpath normalization before hashing.
- **Justify the two-`git rev-parse` claim in the NFR.** Inference needs `--show-toplevel` for cwd, `--show-toplevel` for the configured path, and `--git-common-dir` for both — plus the existing `resolveGitRoot` call. That is four to five invocations, not "at most two," and each carries a 5s timeout, so worst-case startup on a stalled filesystem is 20–25s, not 10s.

## 4. Requirement 6 — "degrades honestly" is exactly what these ACs fail to deliver

The user story asks for a typecheck that "either works or says plainly that it could not run." The ACs deliver a third state the story rules out: a typecheck that runs and lies.

- **Attack AC 6.1 head-on.** Borrowing `tsc` from the workflow root does not make a dependency-less worktree typecheckable. Run it: `tsc -p <worktree>` with no `node_modules` in the worktree resolves no imports, exits non-zero, and emits hundreds of `TS2307: Cannot find module` diagnostics. `runProjectTypecheck` then returns `status: 'success'` with `diagnostics` populated (`src/core/typecheck.ts:180-191`), because the only non-success paths are timeout, overflow, and unparseable output. The review agent receives a wall of fabricated errors and, per its methodology, is invited to fail the task on them. That is worse than the state AC 6.4 preserves.
- **Show that AC 6.6 does not cover this.** It forbids presenting "the absence of diagnostics as a passing typecheck" — a guard against false negatives only. The failure mode AC 6.1 creates is a false *positive* flood. Add an AC that gates the borrowed-compiler path on the worktree's dependencies actually resolving, or drop the borrowing and return a new `reason: 'no-dependencies-in-worktree'`.
- **Add version-skew handling.** A worktree exists to hold a different branch. Borrowing the main checkout's compiler typechecks branch code with the trunk's TypeScript version, and `AC 6.3`'s "distinct indicator that the compiler was borrowed" discloses the borrowing but not the version. Specify what the indicator carries and what the review output does with it, or the disclosure is decorative.
- **Stress-test AC 6.5's side effects.** Moving the cache to `<workspace>/.spec-workflow/.cache` creates a second `.spec-workflow` tree inside every worktree, and three lines from the cache creation sits `ensureGitignoreEntry(projectPath)` (`typecheck.ts:141`), which appends to and rewrites `.gitignore` — a *tracked* file. No AC says which root that call takes. Take the workspace path and every worktree acquires an uncommitted `.gitignore` modification whenever the shared root's entry was never committed. Name the root for that call.
- **Reconcile AC 6.5 with Requirement 7 AC 3.** R7 AC 3 says a worktree "writes to the shared workflow root, preserving the existing sharing behaviour." AC 6.5 requires a worktree-local `.spec-workflow` write. Both cannot be the general rule; state the exception explicitly rather than leaving two requirements to contradict each other.
- **Add the missing tsconfig case.** `tsconfigPath` is derived from the same argument (`typecheck.ts:113`). Redirect to the workspace and a worktree on a branch that has not yet added `tsconfig.json` reports `reason: 'no-tsconfig'` where it previously typechecked fine. That is a behaviour change no AC anticipates.

## 5. Requirement 7 — the identity fix makes the shared-state problem worse, and no AC covers it

- **Attack the omission at `project-registry.ts:147-157`.** `writeRegistry` is read-modify-write over one JSON file using a **fixed** temp path, `${this.registryPath}.tmp`, with no lock. Today N worktrees collapse to one `projectId`, so concurrent `registerProject` calls contend but converge on one entry. After Requirement 1, N worktrees produce N distinct entries created concurrently at startup — strictly more contention, on the exact file R7 is named after. Four agents launched together: two read the same map, each adds its own entry, last `rename` wins, one or more worktrees never appear in the dashboard. R7 has four ACs and none of them is about the write.
- **Challenge AC 7.1 as a statement of intent rather than a testable criterion.** "Each SHALL appear as a distinct entry" describes the desired steady state. Add the criterion that actually needs enforcing: concurrent registration from N processes SHALL result in N entries, and a partially written registry SHALL never be observable by the dashboard watcher (`project-manager.ts:80-86` re-reads on every change event).
- **Retire AC 7.4 or mark it as already satisfied.** `ApprovalStorage` is already constructed with `fileResolutionPath: translatedWorkspacePath` (`project-manager.ts:148-151`) and already resolves workspace-first with a workflow-root fallback (`approval-storage.ts:201-221`). As written the AC implies work that does not exist and pads the requirement count. Say "already true; do not regress" and move on.
- **Add the write that actually races: `tasks.md`.** Two worktrees implementing two tasks from the same spec both mark task status in the one shared `tasks.md`. R7's user story is "parallel work does not silently lose data," and this is the write most likely to lose it. The ACs cover the tsbuildinfo path (AC 7.2) and say nothing about the markdown file that every parallel agent mutates.

## 6. Introduction and scope — two load-bearing claims that do not hold

- **Reverse the "already inconsistent, one side is right" framing.** The Introduction says "the adversarial-review route passes the workspace path (`multi-server.ts:851`) while the adjacent task-review route passes the shared root," presenting the first as the precedent to generalize. It is not a precedent — it is a second bug. `originalProjectPath` is the untranslated workspace path, and the handler above it (`:828`) hands that same path to code that immediately does `getWorkflowRoot` on it. In a worktree, the adversarial route fails to find the document at all. Rewrite the framing: both routes are wrong, in different ways.
- **Challenge the out-of-scope justification directly.** The doc excludes "any persisted record of which worktree owns a spec" on the grounds that "ownership stays derivable from the registry and implementation logs." Neither source supports that. Implementation logs record bare file paths with no root or worktree marker (`implementation-log-manager.ts:199-205`), and registry entries are **deleted** once their last live PID disappears (`project-registry.ts:310-312`). The moment the agent's MCP server exits, ownership is derivable from nothing. Either the exclusion needs a different rationale or the record needs to be in scope.
- **Confront the diff-base question the spec never asks.** `computeTaskDiff` runs `git diff HEAD` (`src/core/task-diff.ts:45-46`). The dominant reason to use a worktree is to commit on a branch. An agent that commits its task work gets an empty diff, `computeDiffMethodologyState` returns `{ kind: 'empty' }` (`review-task.ts:104`), and the reviewer proceeds with no diff at all — the same class of failure the Introduction describes, relocated rather than fixed. Requirement 4 must decide the diff base (`HEAD` vs merge-base with the default branch) or explicitly defer it with a stated consequence.
- **Attack the relative-path asymmetry in R4 AC 3.** Resolving log-recorded relative paths against the workspace path is correct for the agent that wrote them and wrong for anyone else. Logs live in the shared root, so a review triggered from the main checkout — or from worktree B — resolves worktree A's relative paths against the reader's own tree and reviews whichever files happen to exist there. Silent wrong-checkout review, which is the defect this spec is named after.
- **Cost the NFR that recommends `.` in `.mcp.json`.** That line changes the install snippet for *every* user, not just worktree users, and it removes the only signal inference has to check against. On a client that spawns the server with cwd `/` (Claude Desktop has historically done this), `.` resolves to `/`, `resolveGitWorkspaceRoot` finds no repo and returns `/`, and the server attempts to initialize a workspace at the filesystem root. This NFR has no acceptance criteria, no guard, and a blast radius larger than the whole spec.

## Top 5 risks and gaps

1. **The runners have one path field and Requirement 5 needs two.** AC 5.1/5.2 as written redirect `RunOptions.projectPath`, which the runner also uses for `getSpecPath` and `TaskReviewManager` (`task-review-runner.ts:95-96`). Literal implementation makes every dashboard task review in a worktree fail with "tasks.md not found." Non-literal implementation leaves the spawn cwd wrong. Neither reading works.
2. **AC 5.4 points a deleting cleanup job at the wrong root.** `job-scheduler.ts:178` and `:186` are spec-cleanup calls, not runner spawns. The AC contradicts AC 5.5 and R7 AC 3, and following it either breaks automated cleanup or aims it at a directory that does not exist.
3. **The optional-with-silent-fallback design (AC 3.2) lets the primary defect survive implementation.** `TaskReviewRunner` constructs its own `ToolContext` at `:100`; nothing in R3 or R4 covers it, so the fallback fires and the dashboard-triggered review diffs the shared root exactly as before — with the spec marked complete.
4. **Requirement 6 replaces silent failure with confident falsehood.** A borrowed compiler in a `node_modules`-less worktree returns `status: 'success'` with a flood of `TS2307` errors (`typecheck.ts:180-191`). AC 6.6 guards only the absence of diagnostics, so nothing catches it. This inverts the requirement's own user story.
5. **Requirement 7 does not address the write it exists to protect.** `writeRegistry` (`project-registry.ts:147-157`) is an unlocked read-modify-write over one file with a fixed `.tmp` name, and the identity change multiplies concurrent writers from one entry to N. Simultaneous worktree startups will drop entries.

## Top 3 conclusions to challenge or reverse

1. **"The adversarial-review route already passes the workspace path" — reverse it.** The route passes an *untranslated* workspace path to a runner (AC 5.3 correctly catches the translation half) and, at `multi-server.ts:828`, the same path to a handler that needs the workflow root (`adversarial-review.ts:60`). It is not the correct precedent the Introduction makes it; it is broken in worktrees today and stays broken after this spec. Reframe it as a second defect and add an AC for `:828`.
2. **"`workspacePath` is additive, optional, with a fallback to `projectPath`" — reverse the silent part.** The fallback is indistinguishable at runtime from the bug being fixed, and it is guaranteed to fire at the one call site (`task-review-runner.ts:100`) that produces the spec's motivating failure. Make the field required at construction, or require a logged warning when it defaults — otherwise there is no way to test that the fix landed everywhere it matters.
3. **"Borrow the compiler from the workflow root" — reverse it in favour of honest unavailability.** A resolvable `tsc` is not a runnable typecheck; the worktree also needs its dependencies. Given that the entire requirement is titled "degrades honestly," the correct behaviour for a dependency-less worktree is a new, specific `unavailable` reason the review discloses — not a run whose output is indistinguishable from real type errors. Borrowing is a plausible-sounding half-measure that manufactures exactly the false confidence this spec was written to eliminate.

## What's missing — do this before acting on the document

- **Enumerate the runner path contract.** Specify `RunOptions` with two named fields (workflow root, workspace) and state which of the three current uses of `opts.projectPath` takes which. Do the same for `AdversarialRunner` (`adversarial-runner.ts:111`), which has the identical shape.
- **Inventory every `ToolContext` construction site and every code-touching consumer**, then make the list part of the requirement rather than citing five line numbers. `args.projectPath` needs an explicit rule: either add `args.workspacePath` or specify that an argument override disables workspace resolution.
- **Decide the diff base for committed worktree work.** `git diff HEAD` returns nothing once the agent commits. This is the normal worktree workflow, and it silently produces a diff-free review. Either specify a merge-base comparison or state the limitation and the disclosure the review output must carry.
- **Add concurrency ACs for the registry write and for `tasks.md`.** The identity change is what makes both hotter. Unique temp filenames plus a retry or lock for `writeRegistry`; a stated policy for concurrent task-status writes.
- **Write the migration and rollout note.** Changing `projectId` from a shared hash to a per-worktree hash renames every existing worktree project. Dashboard URLs keyed by `projectId`, in-flight approvals, and stored job history all move. Nothing in the document acknowledges that existing users' dashboards will change identity on upgrade.
- **Define the test strategy for the parity ACs.** R3 AC 3, R4 AC 7, and R6's degradation paths all assert "identical to prior behaviour" or a specific failure state, and none is checkable without a worktree fixture. `src/tools/__tests__/review-task.test.ts` is 52 KB of tests with no worktree setup; specify the fixture (create a real worktree in a temp dir, or inject the git calls) before the design phase, or these ACs will ship unverified.
- **Either give the `.mcp.json` = `.` recommendation its own acceptance criteria — including behaviour when cwd is not a repository — or cut it.** As a bare NFR sentence it changes the documented install path for all users with no guard on the failure case.
