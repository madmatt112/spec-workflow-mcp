## Lead finding — the design's own safety mechanism does not exist

Component 2 stakes the entire change on this sentence:

> "Making `workspacePath` required is what forces every construction site to be visited by the compiler — this is the mechanism that prevents the fix from silently not landing."

Read `src/server.ts:93-102`:

```ts
const context = {
  projectPath: this.projectPath,
  dashboardUrl: dashboardUrl,
  lang: this.lang
};
this.setupHandlers(context);
```

and `src/server.ts:135`:

```ts
private setupHandlers(context: any) {
```

The object literal has no type annotation and is passed to a parameter typed `any`. **Making `workspacePath` required on `ToolContext` produces zero compiler errors at this site.** This is the one construction site R3 AC 3 names by number, the site the requirements identify as holding the already-known worktree path (`src/server.ts:61` — verified, `this.workspacePath = workspacePath`), and the site whose omission reproduces the exact defect the spec exists to fix. The compiler will not catch it.

The mechanism works at `task-review-runner.ts:100` (`const context: ToolContext = {…}` — annotated) and at `multi-server.ts:828` (contextually typed by `adversarialReviewHandler`'s signature). It fails at the only one that matters. Fix the design to require annotating `context` as `ToolContext` and changing `setupHandlers(context: any)` to `setupHandlers(context: ToolContext)`, or drop the claim.

Related: `src/tools/__tests__/spec-index.test.ts:79` passes `{} as ToolContext`. A type assertion silences the required field there too. R3 AC 2 says "including test fixtures"; the design's Integration Points list stops at `src/server.ts:96` and enumerates nothing else. Four other annotated fixtures exist (`prompts/__tests__/create-steering-doc.test.ts:5`, `tools/__tests__/decomposition-guide.test.ts:6`, `tools/__tests__/projectPath.test.ts:10,41,74,134`).

## 1. `SharedWorkflowResources` lifecycle (Component 6)

**The refcount has no critical section, and the sync loop is already re-entrant.** `startRegistryWatcher` (`project-manager.ts:80-86`) registers two handlers — `on('change')` and `on('add')` — that both call `await this.syncWithRegistry()` with no re-entrancy guard, no queue, no in-flight flag. `addProject` awaits at `:155` (`watcher.start()`) and `:156` (`approvalStorage.start()`) before inserting into `this.projects` at `:193`. Concrete failure: two worktrees register within the chokidar debounce window; two `syncWithRegistry` invocations interleave; both call `addProject` for distinct projectIds on the same workflow root; both find `sharedByRoot` empty; both construct a `SpecParser`+`SpecWatcher`+`ApprovalStorage`+`SpecArchiveService`; the second `Map.set` orphans the first set with two live chokidar watchers and no handle to stop them. R10 AC 1 ("SHALL share one") is violated at exactly the moment the requirement exists to handle — N worktrees starting together. The design specifies the refcount as a `Set<string>` mutated across await boundaries and never mentions serialization.

**The teardown/reconstruct race is real but the pass ordering saves you — say so and move on.** `syncWithRegistry` adds (`:106-121`) before it removes (`:124-128`), so within one pass a root whose last old entry is dropped and whose new entry is added keeps `projectIds` non-empty throughout. That specific concern is fine. It is fine only because of an incidental statement ordering that nothing pins; add a test.

**Error Scenario 7 describes a failure mode that cannot occur.** The design claims a removed worktree directory causes "component construction for that entry [to] fail" and be caught at `:198-200`. Read `addProject:146-152`: all four components are constructed from `translatedWorkflowRootPath`. `ApprovalStorage`'s constructor only `resolve()`s `fileResolutionPath` — a pure string operation, no `fs` call (`approval-storage.ts:140`). `approvalStorage.start()` mkdirs under the **workflow** root (`:141`, `:146`). **No code path in `addProject` touches the workspace directory on disk.** A removed worktree therefore produces no failure at all. The Reliability NFR's removed-worktree case, which R12 AC 6 requires a test for, will pass vacuously against a scenario that never fires. Either find the real failure mode (it is downstream — the runner's `spawn({ cwd: workspacePath })` throws `ENOENT`, and `computeTaskDiff`'s `runGit` returns `ok: false` and silently yields an empty diff) or delete the scenario.

**Watcher-failure isolation inverts under sharing, and the design does not say which way.** Today a `watcher.start()` throw kills exactly one project. Under sharing, the first project on a root owns construction. If its `start()` throws, the catch at `:198-200` swallows it — and whether the half-built `sharedByRoot` entry was inserted before or after `await start()` decides whether every subsequent project on that root inherits a dead watcher or retries construction. The design specifies neither insertion point nor rollback. Specify: insert only after both `start()` calls resolve, and on throw delete the partial entry.

**Ordering between `project-added` and the first `spec-change` is now non-deterministic.** Today the shared watcher is started (`:155`) before `this.emit('project-added')` (`:197`) for that project, so the frontend's project list is populated before its first `spec-change`. Under sharing, project #2 on a root emits `project-added` while the shared watcher has been running for arbitrarily long — a `spec-change` carrying project #2's id can be broadcast *before* the frontend knows project #2 exists. The design's `projectIds: string[]` fan-out makes this the normal case, not an edge case, and says nothing about it.

**Two projects with different Docker translations on one root is unrepresentable.** `PathUtils.translatePath` (`path-utils.ts:108`) is driven by a single process-global `SPEC_WORKFLOW_HOST_PATH_PREFIX`/`_CONTAINER_PATH_PREFIX` pair, so within one dashboard process two workflow roots cannot translate differently. That half is fine. The other half is not: `sharedByRoot` is keyed on the *translated* root, so if two distinct host workflow roots (`/host/a` and `/host/b`) both live under the same host prefix and collapse onto one container path, they share components and each other's specs. Unlikely, but the design asserts the key is safe without argument. Key on the untranslated `entry.workflowRootPath` and translate for construction only.

## 2. `ApprovalStorage` per-project resolution (Component 6)

**The claim is false as written.** The design says `ApprovalStorage` can "keep per-project `fileResolutionPath` behaviour by resolving against the *requesting* project's workspace at read time rather than at construction." `fileResolutionPath` is an instance field (`approval-storage.ts:107`, set at `:140`) consumed by the private `getFilePathCandidates` (`:204-227`), which takes only `filePath`. To resolve per-request you must thread a workspace argument through `resolveExistingFilePath` and `resolveFilePathForWrite` and out to every public method that reaches them: `captureSnapshot(approvalId, trigger)` (`:558`), `getCurrentFileContent(approvalId)` (`:682`), `compareSnapshots(approvalId, from, to)` (`:698`), `createRevision(originalId, newContent, reason?)` (`:410`), and `updateApproval(id, status, response, annotations?, comments?)` (`:341`, which calls `captureSnapshot` at `:356` and `:362`). **That is five public signature changes.** The design's "without changing its public interface" is not qualified anywhere and is wrong.

**Sixteen dashboard call sites must supply the workspace.** `multi-server.ts:224, 272, 404, 689, 711, 794, 811, 892, 944, 1044, 1095, 1179, 1212, 1232, 1273, 1288`. Most reach `project` from `getProject(projectId)` so the workspace is available — but `:404` is inside the `approval-change` broadcast handler, which under Component 6 receives a *shared* event and no longer has a single requesting project. That is the one site where the design's claim structurally fails, and it is the site R10 AC 2 is about.

**The path validator will start throwing.** `getFilePathCandidates:218-224` calls `PathUtils.validatePathWithinBases(candidate, [fileResolutionPath, projectPath])`. A shared instance carrying worktree A's `fileResolutionPath` handed worktree B's relative path resolves the candidate under A and passes only because both live under the same repo — until a nested layout or a sibling outside the workflow root, where it throws `Path traversal detected` instead of returning `null`. `resolveExistingFilePath` catches nothing (`:229-240` only catches `fs.access`); the throw propagates out of `getCurrentFileContent` → `compareSnapshots` → a 500 on the diff route.

**R11 AC 9 does regress, and the regression is invisible.** AC 9 exists "to prevent regression, not to request work." The shared instance can only hold one `fileResolutionPath`. Whichever project constructed it wins; every other project on that root silently gets that project's workspace as candidate #1. Because candidate #2 is the workflow root and `.spec-workflow` files live there, `resolveExistingFilePath` will usually still find *a* file — the wrong one, from a sibling worktree, with no error. This is the identical failure class the spec exists to fix, reintroduced by the component that pays for the fix.

**`src/tools/approvals.ts:216` and `:385` are a second construction site the design never mentions**, and they already pass `fileResolutionPath: translatedPath` — the workflow root, not a workspace. So the MCP-side approvals path has *never* had the workspace-first behaviour R11 AC 9 protects. Once `ToolContext` carries `workspacePath`, that site becomes wrong-by-omission. Enumerate it.

## 3. The diff-base recording hook (Component 9, Requirement 5)

**The hook fires almost never, and the design says so without drawing the conclusion.** The only recording site is the dashboard's `PUT /api/projects/:projectId/specs/:name/tasks/:taskId/status` (`multi-server.ts:1404` — verified). R5 AC 8 and Component 9 both concede agents set status by editing `tasks.md` directly. So the base is recorded only when a human clicks a status control in the dashboard. Component 9 buys a new module (`TaskStateStore`), a new on-disk format, a new `computeTaskDiff` parameter, two new `ExecutionContext` states, and a new `git rev-parse --verify` call — to serve a path that fires on a minority of task starts, while the fallback path it also builds is the one that runs. That is not a reason to drop it, but the design must justify the complexity against the actual hit rate, and it does not attempt to.

**Nothing establishes *which* repository's `HEAD` gets recorded.** `TaskStateStore.recordBase(taskId, commit)` takes a commit; something must produce it. The endpoint runs inside the dashboard process. `project.workspacePath` is Docker-*translated* (`project-manager.ts:143`), so under path translation the dashboard would `git rev-parse HEAD` in a container path that may not be a checkout. The design specifies no producer, no cwd, and no failure behaviour.

**A worktree that shares the workflow root will read another worktree's base, and the resolvability check cannot catch it.** `<specPath>/.task-state/` lives under the *shared* `.spec-workflow`. Worktree A marks task 3 in-progress → A's `HEAD` written. Worktree B reviews task 3 → reads A's commit. `git rev-parse --verify <A-sha>^{commit}` run in B **succeeds**, because linked worktrees share one object database. So the `base-unresolvable` guard never fires, and `git diff <A-base> -- <files>` in B renders the entire divergence between the two branches as "this task's work". The design's own attribution machinery cannot save you here: `TaskState` is one file holding `baseCommit` and `workspacePath` together with merge-then-replace semantics, so B's `recordAttribution` overwrites `workspacePath` to B while `baseCommit` still holds A's SHA — a record that reports `attribution: match` alongside a foreign base. **This is the spec's headline defect, reproduced by the spec's own fix.** Key the base by workspace, or store it per-workspace.

**The commit-resolves-but-is-unrelated case needs `--is-ancestor`, not `--verify`.** Same object database, rebased branch, cherry-picked history: `rev-parse --verify` passes on any object that exists. The minimum honest check is `git merge-base --is-ancestor <base> HEAD`; on failure, fall back to `HEAD` with a distinct reason. The design's single check is the weakest one available.

**`TaskStateStore`'s contention argument is right about the wrong axis.** `3.2` → `3-2` and `3.2.1` → `3-2-1` under `replace(/[/.]/g, '-')` (`task-review-manager.ts:72`) — distinct filenames, no collision. Fine. But the contention that matters is **N worktrees writing the same task's file through one shared `.spec-workflow`**, and `recordBase`/`recordAttribution` are both unguarded read-merge-write cycles — the exact race the design bothered to fix for `activeProjects.json` (Component 7) and left unfixed one component earlier. Note also that `1.2` and `1/2` both sanitize to `1-2`; task IDs are documented as dotted, so this is latent, not live.

## 4. The TS2307 flood detector (Component 8)

**`TS2688` is largely unreachable, so the code set is effectively `{TS2307}`.** `parseTscOutput`'s `DIAGNOSTIC_HEADER_RE` (`typecheck.ts:272`) is `/^(.+?)\((\d+),(\d+)\): error TS(\d+): (.+)$/` — it requires a `file(line,col)` prefix. `tsc` emits `TS2688` ("Cannot find type definition file for 'node'") as a **global** diagnostic with no file position: `error TS2688: …`. That line does not match, is not consumed, and is not pushed. The design's ratio arithmetic is therefore over a set that in practice contains only `TS2307`. The design's stated rationale ("a broken `node_modules` … produces resolution failures almost exclusively") survives, but the `TS2688` half of the predicate is dead code. Verify with a real broken-`node_modules` fixture before shipping the constant.

**`TypecheckDiagnostic.code` does hold `"TS2307"`, not a number** — `parseTscOutput:308` writes `code: 'TS' + codeNum`. The design is correct here. Move on.

**Both thresholds are defeatable, in both directions, by ordinary cases.**
- *Under the floor:* a small worktree — say four modified files importing three workspace packages — with `node_modules` absent produces 6–9 `TS2307`s. `d.length < 10` → detector returns false → `status: 'success'` with nine fabricated "Cannot find module" errors and `inScope: true` on every one, which routes to `R4_4_TYPECHECK_PRESENT` and instructs the reviewer to "promote to a finding". The design ships a fabricated-`fail` verdict for exactly the small-worktree case R7 exists to protect.
- *Over the ratio:* rename a barrel file. A refactor that moves `src/core/index.ts` yields 40 `TS2307`s across importers plus 6 genuine type errors: 40/46 = 0.87 ≥ 0.8 → the run is declared `unavailable` and **six real type errors are discarded**. R7 AC 3 asks for the flood case; the design's predicate cannot distinguish "no compiler could resolve anything" from "a large legitimate move".
  The structural fix is not a better ratio — it is to check whether `node_modules` resolution is broken *directly* (does `<workspace>/node_modules/typescript/lib` exist; did `listFiles` include any `node_modules` `.d.ts`) rather than inferring it from diagnostic shape. `run.stdout` already carries `--listFiles` output and `parseTscOutput` already returns it (`:316-321`) — the signal is free and the design ignores it.

**Returning `unavailable` silently drops `inScope`, `coverage`, `truncated`, and `suppressedDenylistedFiles`.** The `unavailable` arm (`typecheck.ts:25-40`) carries only `tsconfigPath`, `status`, `reason`, `rejectionMessage?`. Callers narrow correctly today — `computeTypecheckMethodologyState:122-127` returns early — so nothing crashes. But the design places the detector "after `parseTscOutput` and before the `status: 'success'` construction at `:180-191`", which is **after** the `await postProcess(…)` at `:178`. `postProcess` runs `realpathChunked` over every diagnostic file and every `--listFiles` entry (`:205-206`, `:236`) — thousands of `fs.realpath` calls — and then the design throws the result away. Run the detector on the raw `diagnostics` immediately after `parseTscOutput:168` and short-circuit. The design must also state whether the ratio is computed over raw diagnostics or over `post.diagnostics`, which is denylist-filtered and capped at 100 (`DIAGNOSTIC_CAP`, `:260-261`) — the two give different ratios.

**The new reasons do not reach the reviewer, and there is a pinned-prose test in the way.** `R4_6B_TYPECHECK_UNAVAILABLE` (`review-task.ts:724-725`) enumerates the reason strings verbatim: `'project-references'`, `'no-tsconfig'`, `'tsc-not-found'`, `'no-parseable-output'`, `'output-overflow'`, `'rejection'`. `'unresolved-dependencies'` and `'no-tsconfig-in-workspace'` are not there. Worse, the comment at `review-task.ts:713-714` states these constants are "verbatim prose from requirements.md … so the prose remains byte-identical to R4 (drift test)", and `src/tools/__tests__/review-task.test.ts:1293` runs a two-way drift test against `.spec-workflow/specs/tighter-reviews/requirements.md` — a **different spec's** requirements file, which `:1291` notes is gitignored (so the test is `skipIf`-disabled in a fresh clone and live on the maintainer's machine). Editing `R4_6B` to name the new reasons requires editing that other spec's requirements document. The design does not mention the constant, the drift test, or the cross-spec dependency.

**`ensureGitExcludeEntry` will write to the wrong directory.** `git rev-parse --git-common-dir` returns the bare relative string `.git` when run from a repository root — verified in this repo just now. `path.join('.git', 'info', 'exclude')` is relative and resolves against `process.cwd()`, which for an MCP server is the client's launch directory. This is the identical trap `resolveGitRoot` guards at `git-utils.ts:53` and `:60-66`; the design routes that normalization only into Component 1's `rawGitCommonDir` and leaves Component 8 to call raw `git rev-parse`. Additional unaddressed cases: (a) non-git project — the design specifies no catch, and `typecheck.ts` currently imports no git at all, so this adds a `git` process invocation to the typecheck hot path; (b) `git init` templates that omit `info/exclude`, where the current function's "no file → do not create" policy (`:382-388`) means the entry is never written; (c) bare repos and `--git-dir` overrides.

**The design invalidates R7 AC 9's rationale and then repeats it.** R7 AC 9 requires the fixture's committed `.gitignore` to omit `.spec-workflow` because `ensureGitignoreEntry` early-returns when covered (`:391-396`) — and this repo's `.gitignore:148` does contain `.spec-workflow` (verified). But Component 8 says "the existing early-return-if-covered check is kept, **reading the exclude file instead of `.gitignore`**." Once the check reads `info/exclude`, a committed `.gitignore` containing `.spec-workflow` is irrelevant to whether the entry is written. The design nonetheless restates the rationale verbatim at line 328: "Its fixture repository's committed `.gitignore` deliberately omits `.spec-workflow`, without which the `info/exclude` behaviour is unreachable in test (R7 AC 9)." That sentence is false under the design's own Component 8. Separately, the existing e2e fixture (`e2e/helpers/worktree-harness.ts:135-139`) commits only `README.md` and has **no `.gitignore` at all**, so the constraint is already satisfied by accident.

## 5. Registry optimistic concurrency (Component 7)

**Read-hash-write-rename narrows the window; it does not close it, and R11 AC 2 is a `SHALL`.** There is no compare-and-swap in POSIX `rename` and none in Node's `fs`. Between this process's final re-read+hash and its `fs.rename`, another process can complete its own rename. Concrete exhaustion-free data loss: N=2 worktrees start with no `activeProjects.json` present. Both `readRegistry` hit `ENOENT` and return an empty `Map` (`project-registry.ts:120-124`). Both hash "absent". Both re-read, both still observe absent, both write their unique temp, both rename. **Second rename wins; the first worktree's entry is gone and neither process retries or errors.** That is R11 AC 2's exact scenario — "WHEN N MCP server processes register concurrently … THEN the registry SHALL contain N entries" — failing on the very first registration, with no diagnostic. A probabilistic narrowing does not satisfy a `SHALL`. The correct primitive is an exclusive lock: `fs.open(lockPath, 'wx')` or `fs.link()`-based, held across read-modify-write, with a stale-lock timeout. It costs nothing in dependencies (the NFR permits `fs`) and it is the only construction that makes AC 2 true.

**Two more unlocked read-modify-write cycles are left out.** The design says "Both `registerProject` and `cleanupStaleProjects` wrap read-modify-write in an optimistic loop." `unregisterProject` (`:233-255`) and `unregisterProjectById` (`:260-264`) are also unlocked read-modify-write cycles that **delete** and call `writeRegistry`. N worktrees shutting down concurrently, or one shutting down while another registers, drops entries by the same mechanism R11 AC 4 identifies for `cleanupStaleProjects`. `removeProjectById` (`project-manager.ts:293-296`) reaches `unregisterProjectById` from the dashboard's delete route. Enumerate all four writers or state why two are exempt.

**5 attempts × 10–50 ms is not sized against anything.** No arrival model is given. With N writers each holding the file for one read+serialize+write+rename (~1–3 ms on tmpfs, tens of ms on a networked `$HOME`), and jitter drawn from a 40 ms window, exhaustion becomes likely somewhere around N ≈ 8–12 on a slow filesystem — a plausible number for a parallel-agent workflow, which is the stated use case. State the model or make the retry budget time-bounded rather than count-bounded.

**Throwing on exhaustion is worse than the alternative the design rejects.** `registerProject` is awaited inside `SpecWorkflowServer.initialize` (`server.ts:76`), inside the `try` that wraps workspace validation and transport connection. A throw there aborts `initialize` before `StdioServerTransport` connects (`server.ts:105`), so the MCP client sees the server process die during handshake — surfaced to the user as "MCP server failed to start", with the real cause (`activeProjects.json` contention) buried in stderr the client may not display. R11 AC 5's intent ("fail loudly … rather than starting unregistered and invisible") is defensible; the design's realization of it takes the whole MCP server down over a dashboard-visibility concern. Prefer: log loudly, continue unregistered, and expose the state — or, better, use a real lock so exhaustion stops being a scenario.

**AC 6 is satisfied by AC 1, not by rename atomicity — the design credits the wrong fix.** Component 7's Atomicity paragraph argues that `rename` is atomic so "the watcher never observes a partial file." The current corruption vector is not a torn rename; it is two writers `fs.writeFile`-ing the **same** `${registryPath}.tmp` (`:154`) concurrently and interleaving bytes, after which an atomic rename installs a syntactically invalid file. The unique-temp-name change (AC 1) is what fixes AC 6. Rename atomicity was never in question. Also worth noting: `readRegistry` already handles the corrupted case gracefully (`:125-139`, backing up to `.corrupted.<ts>`), so AC 6's blast radius today is smaller than the requirement implies.

## 6. Traceability and the pieces with no home

**R9 AC 5 has no implementable home.** `AdversarialRunner` does not build a prompt. Its entire prompt is `Read and execute the instructions in ${opts.promptOutputPath}` (`adversarial-runner.ts:110`), a pointer to a scaffold file written by `adversarialReviewHandler` *before* `run()` is called (`:100-105` asserts the file exists). So "`AdversarialRunner` renders the same block" (Component 4) assigns work to a component that has no prompt to render into. Beyond the plumbing, the `ExecutionContext` type has **no valid inhabitant** for an adversarial run: `diffBase` is a required two-arm union with no `not-applicable` case, `attribution` requires a task-derived state, and `typecheck` requires a `TypecheckResult['status']` from a typecheck that never ran. Either give `ExecutionContext` an adversarial shape (workspace + workflow root only) and let `renderExecutionContext` degrade, or move the disclosure into `adversarialReviewHandler`'s scaffold writer and say so.

**R4 AC 6's containment answer over-grants, and the design's own Security NFR contradicts it.** "Containment is a membership test against both roots" means: accept if under the workspace **or** under the workflow root. In the nested layout R4 AC 6 names (`~/repo/worktrees/a`), the workflow root is `~/repo` — which contains `~/repo/worktrees/b`, `~/repo/worktrees/c`, and every other agent's checkout. During a review of worktree A, any path in worktree B passes containment through the workflow-root arm, and nothing in the design prevents it. The Security NFR asserts "Containment accepts the workspace path and the workflow root, and no ancestor of either" — but in a nested layout the workflow root *is* an ancestor of every sibling worktree, so the NFR's guarantee and the design's rule are mutually exclusive. R4 AC 6 asks only that `.spec-workflow` paths above the workspace be accepted. The narrow rule that satisfies it without opening sibling worktrees is: accept under `workspacePath`, **or** under `join(workflowRoot, '.spec-workflow')`. Adopt that.

**Requirement 8 has an interface and no integration point.** `TaskStateStore.recordAttribution` exists in Component 3. Nothing calls it. `src/tools/log-implementation.ts` appears in the design exactly once — inside a quotation of R3 AC 4's override list — and is absent from Integration Points, from Components, and from the Testing Strategy except as a restatement of R12 AC 6. Further, R8 AC 1 requires the entry to record "the absolute workspace path the work was performed in, **and the `HEAD` commit at logging time**." The `TaskState` data model has `workspacePath`, `workspaceSource`, `lastLoggedAt` — **no HEAD commit field at all.** R8 AC 1 is unimplementable against the design's own data model. R8 AC 2's override-derived marking maps to `workspaceSource: 'override'`, which is the one part that lands.

**R1 AC 11 is silently dropped.** It requires `--no-workspace-inference` be added to the valid-flag list at `src/index.ts:115` (verified — `const validFlags = ['--dashboard', '--port', '--help', '-h', '--no-open', '--no-shared-worktree-specs']`) and to the argument filter at `:166-175`, and states the consequence of omission: the flag survives filtering, becomes `filteredArgs[0]`, and the server registers a project whose path is the literal string `--no-workspace-inference`. Actually it is worse than the requirement states — the loop at `:116-128` **throws** `Unknown option: --no-workspace-inference` before filtering is reached, so the server refuses to start. The design's Integration Points names only `src/index.ts:180-181` ("the sole CLI resolution site") and never mentions `:115` or the filter. No component owns this criterion.

**R1 AC 9 and R2 AC 5 cannot both hold given the signature.** `resolveWorkspaceRoots(opts: { configuredPath, cwd, noInference, noSharedWorktreeSpecs })` has no dashboard-mode parameter. R1 AC 9 requires inference skipped in `--dashboard`; R2 AC 5 requires `SPEC_WORKFLOW_WORKSPACE` **ignored** in `--dashboard`. Folding dashboard mode into `noInference` satisfies the first and not the second, because the stated precedence (`env` → flag → inference → argument, R2 AC 3) puts the env var *above* the flag. Add a `dashboardMode` parameter, or state that `index.ts` must not call the function at all in dashboard mode.

**The `--no-shared-worktree-specs` × inference interaction is unspecified and probably a regression.** Today (`index.ts:180-181`): `workflowRootPath = noSharedWorktreeSpecs ? workspacePath : resolveGitRoot(workspacePath)` — the flag means "put `.spec-workflow` in the workspace." The design states `workflowRootPath` is "**always** computed from `configuredPath`, never from an overridden workspace (R2 AC 4)." Under inference in a worktree, `configuredPath` is the main repo (the `.mcp.json` value) and the workspace is the worktree — so `--no-shared-worktree-specs` now yields the **main repo's** `.spec-workflow`, the exact opposite of the flag's documented meaning ("Shared worktree specs disabled. Using workspace-local `.spec-workflow`", `index.ts` stderr). `noSharedWorktreeSpecs` is a declared parameter of `resolveWorkspaceRoots` and its behaviour is never described. This also silently breaks the existing e2e worktree suite, which runs exclusively in that mode.

**R12 AC 6 lists nine behaviours; three have no owning component.** R2 AC 6 (env scrubbing) → Component 5 ✓. R3 AC 4 → Component 2 ✓. R4 AC 3-8 → Component 10, partially (AC 7's mismatch detection depends on R8's missing writer). R6 → Component 5 ✓. **R8 (attribution round-trip) → no writer.** R9 (execution context reaching `buildPrompt`) → Component 4 for the task path; **no viable owner for the adversarial path**. R10 → Component 6 ✓. **Reliability NFR removed-worktree case → the scenario does not exist (see §1).**

**Nothing owns migration, and `ToolContext.workspacePath` is a breaking change for external callers.** `ToolContext` is exported from `src/types.ts` and the package ships built `.d.ts`. Making a field required is a semver-major change for any consumer constructing one. The design's Migration NFR covers `projectId` stability and pre-upgrade task state; it says nothing about the type change, nothing about a deprecation window, and no component owns it. State a position: either it is internal-only (then say so in the package docs) or it is a major bump.

## Additional grounded findings the six dimensions do not cover

**The "one frontend touch point" claim is wrong in both directions.** The design says the change is "the dashboard's event filter … from `event.projectId === selected` to `event.projectIds.includes(selected)`." What is actually there:

1. `ProjectManager`'s forwarded events (`:159-176`) are **internal**. The frontend never sees them. Five handlers in `multi-server.ts` translate them into WebSocket messages: `spec-change` (`:345-374`), `task-update` (`:378-381`), `steering-change` (`:384-397`), `approval-change` (`:399-412`), `deferral-change` (`:436+`). All five destructure `const { projectId } = event`. **All five must change; the design names none of them.**
2. Filtering is done **server-side** by `broadcastToProject` (`:2103-2115`), which matches `connection.projectId === projectId`. The frontend's `WebSocketProvider.tsx:93,104` re-checks `msg.projectId === targetProjectId` as a second filter.
3. Because each subscribed client expects a message whose `projectId` equals its own subscription, an event on a shared root **cannot** be broadcast as a single message carrying `projectIds: string[]` without breaking that contract. The correct shape is: one shared event → loop `projectIds` → `broadcastToProject(id, { …, projectId: id })`. Under that shape **the frontend needs no change at all** — the design's single named touch point is the one thing that does not move.
4. `pendingSpecBroadcasts` (`:348`, `:356`, `:373`) is a debounce `Map` keyed by `projectId`. Changing the event payload to an array without rekeying it silently degrades or breaks spec-change coalescing.
5. `broadcastTaskUpdate(projectId, specName)` (`:2165`) re-reads task state per project. With N entries on one root, a single `tasks.md` save still does N reads unless deduped — the hottest event path, and the one R10 exists to flatten, is untouched by the design.
6. The built frontend bundle is committed (`src/dashboard_frontend/dist/assets/index-*.js`). Any frontend change needs a rebuild in the same commit.

**R10 AC 2 as written ("broadcast it once per workflow root") is not implementable against the per-connection projectId contract.** Reading it literally breaks the frontend filter. Reading it as "read the tree once, send per subscriber" is implementable and is what the cost argument actually needs. The design should say which reading it adopts; it currently quotes AC 2 and asserts "emitted **once**".

**Two-root file resolution will silently empty the diff for every doc-authoring task in a sibling worktree.** This is the sharpest consequence of the design and it is unaddressed. R4 AC 3 requires logged `.spec-workflow/specs/…` paths to resolve via the workflow-root fallback and be kept in `filesToReview`. `handlePrepare:389` passes that same `validatedAllFiles` array to `computeTaskDiff`, which runs `git diff -U10 -M HEAD -- <paths>` with `cwd = workspacePath` (`task-diff.ts:44-45`, `runGit:21-32`). In a sibling layout (`~/repo` and `~/repo-wt-a`), a resolved path like `~/repo/.spec-workflow/specs/x/design.md` is **outside** `~/repo-wt-a`; git exits non-zero with "is outside repository"; `runGit` returns `ok: false`; `computeTaskDiff:53-55` returns `{ diff: '', stats: undefined, truncated: false }` **with no rejection field**. One out-of-worktree pathspec therefore discards the entire diff for that review, and `computeDiffMethodologyState` classifies it as `'empty'` — the benign arm — so the reviewer is told "the task changes were already committed before review", which is false. The fix is to partition `validatedAllFiles` by which root resolved it and pass only workspace-resolved paths to `computeTaskDiff`. The design never partitions.

**The same split inflates typecheck coverage gaps.** `runProjectTypecheck(workspace, validatedAllFiles, …)` intersects `allFiles` against `--listFiles` in `postProcess:217-233`. Workflow-root-resolved `.md` paths land in `coverage.excluded`, which flips `computeTypecheckMethodologyState:129,135` to `success-partial-coverage`, which injects `R4_5_TYPECHECK_PARTIAL_COVERAGE` ("degraded review surface") into every doc-authoring review. R3 AC 6's parity claim ("the set of files typechecked … identical to the pre-change behaviour") holds only when the roots are equal; the worktree case regresses the methodology text with no disclosure.

**`degraded` will be true for essentially every review, forever — and the design's own migration note says otherwise.** `degraded = fallback diff base || typecheck ≠ success || attribution ≠ match`. Component 9 concedes direct `tasks.md` edits record no base and calls that "the common case today"; R5 AC 8 calls it "the dominant case" and "not separately solvable within this spec." So the `fallback-head` arm is permanently on for the dominant path. R9 AC 4 then requires the prompt to "instruct the agent to qualify its verdict … rather than treating the run as clean" — on every review, in every project, worktree or not. **A degradation flag that is always set carries no information, and it trains reviewing agents to discount the disclosure.** The Migration NFR compounds the error: "This is expected and self-clearing as tasks are re-logged." Attribution self-clears on re-log; the **diff base does not**, because R5 AC 8 says nothing re-records it. The design contradicts itself across two sections. Separate "expected baseline" (no base recorded — the norm) from "degraded" (base recorded and lost, typecheck unavailable, attribution mismatch), and let only the latter trigger the qualify-your-verdict directive.

**The disclosure channel duplicates one that already exists, with no reconciliation.** `buildReviewMethodology` already emits degradation directives for the diff (`R4_2A_DIFF_EMPTY`, `R4_2B_DIFF_REJECTED`), the typecheck (`R4_6A`, `R4_6B`, `R4_7`), and coverage (`R4_5`). Component 4 adds a second `## Execution Context` block stating typecheck status and diff-base state again. Two channels, populated independently, will disagree — e.g. `R4_2A` says "already committed before review" while the execution context says "fallback-head, no-base-recorded". Decide which channel owns which fact.

**`handlePrepare` must return the execution context in `data`, not `projectContext`, and the design does not say so.** R9's design note is explicit that `projectContext` (`review-task.ts:430-435`) is discarded. `task-review-runner.ts:110` destructures from `prepareResponse.data`. Component 4 says only "`handlePrepare` returns it." Name the field.

**Component 10 targets the wrong function.** It says two-root resolution "replaces the single-root resolve at `:361`". Line 361 is `.map(p => path.resolve(projectPath, p))` — pure string resolution, no filesystem probe. The `realpath` the design's rule depends on ("the first that `realpath`s wins") happens inside `validateAllFiles` at `:64`. The rule cannot be implemented at `:361` as written; it belongs in `validateAllFiles`, which must then take two roots and return which root won per path (see the diff-partitioning finding above). `validateAllFiles` is exported and directly unit-tested — its signature change is a test-surface change the design does not flag.

**The e2e harness cannot exercise inference, and "extends" understates the work.** `worktree-harness.ts:200` spawns `npm run dev -- <projectPath> --no-shared-worktree-specs` with `cwd: this.options.serverRoot` — the spec-workflow-mcp repo itself. Under the design's inference rule, `rawGitCommonDir(configuredPath)` (the temp fixture) and `rawGitCommonDir(cwd)` (this repo) differ, so inference never fires. The harness must set the child's `cwd` to the worktree. Separately, `seedWorktreeA`/`seedWorktreeB` (`:151-190`) place `.spec-workflow` **inside each worktree** because the harness runs in `--no-shared-worktree-specs` mode; a shared-mode harness needs it in `repo-main` only, with nested-layout support added. That is a rewrite, not an extension. R12 AC 1 also requires nested layouts, which the harness does not have.

## Top 5 risks/gaps

1. **The compiler cannot enforce the change at the site that matters.** `setupHandlers(context: any)` (`server.ts:135`) and the unannotated literal at `:93` mean a required `ToolContext.workspacePath` produces no error at the MCP server's own construction site. The design's stated anti-regression mechanism does not fire where the defect lives.
2. **Registry optimistic concurrency cannot satisfy R11 AC 2.** Two processes starting against a nonexistent `activeProjects.json` both observe absence at every check and both rename; one registration is lost with no retry and no error. Hashing narrows a TOCTOU window it cannot close. An exclusive lockfile is required. `unregisterProject` and `unregisterProjectById` are additionally left unprotected.
3. **The shared diff base reproduces the defect the spec exists to fix.** `<specPath>/.task-state/` is on the shared workflow root with no workspace key, so worktree B reviewing a task started in worktree A diffs against A's commit — and `git rev-parse --verify` **succeeds**, because linked worktrees share one object database, so the `base-unresolvable` guard never fires. A confident verdict is returned about a cross-branch diff.
4. **Two-root file resolution silently empties the diff for doc-authoring tasks in sibling worktrees.** The workflow-root-resolved `.spec-workflow` paths R4 AC 3 requires are passed unpartitioned into `git diff -- <pathspec>` run with `cwd = workspacePath`; git rejects the out-of-tree path, `runGit` returns `ok: false`, and `computeTaskDiff:53-55` discards the whole diff with **no rejection field**, so the reviewer is told the benign "already committed" story.
5. **`SharedWorkflowResources` refcounting has no critical section against an already-re-entrant sync loop.** `syncWithRegistry` is invoked from two unguarded chokidar handlers and `addProject` awaits twice before publishing state, so concurrent worktree registrations on one root construct duplicate component sets and leak watchers — failing R10 AC 1 at precisely the N-worktrees-start-together moment the requirement exists for.

## Top 3 conclusions to challenge or reverse

**1. Reverse: "This is the one frontend touch point."** The frontend filter (`WebSocketProvider.tsx:93,104`) is the one thing that need not change. Five server-side handlers in `multi-server.ts` (`:345`, `:378`, `:384`, `:399`, `:436`) destructure `event.projectId` and must all change, `broadcastToProject:2103` filters by connection, and `pendingSpecBroadcasts` is keyed by `projectId`. Because each subscriber expects a message whose `projectId` matches its own subscription, a single message carrying `projectIds: string[]` breaks the contract. Correct design: keep the WebSocket message shape exactly as it is, change only the internal `ProjectManager` event to carry `projectIds`, and have each `multi-server` handler loop and emit per-subscriber. R10 AC 2's cost goal is met by reading the tree once, not by sending once. This also removes the frontend change entirely — including the committed `dist` rebuild.

**2. Reverse: `degraded` as currently defined.** With `fallback-head` in the disjunction and Component 9 conceding that no base is recorded in the dominant case, `degraded` is permanently true and R9 AC 4's qualify-your-verdict directive fires on every review in every project. That is not disclosure; it is noise that teaches agents to ignore the block. The Migration NFR's "self-clearing" claim is false for the diff-base arm by R5 AC 8's own admission. Split the concept: `baseline` (no base recorded — the norm, disclosed factually, no directive) versus `degraded` (base recorded and lost, typecheck unavailable, attribution mismatch — directive fires). Then reconcile against the *existing* degradation channel in `buildReviewMethodology`, which already emits `R4_2A`/`R4_5`/`R4_6B`/`R4_7` and will otherwise contradict the new block.

**3. Challenge: `ApprovalStorage` can be shared "without changing its public interface."** It cannot. Five public methods (`updateApproval`, `captureSnapshot`, `getCurrentFileContent`, `compareSnapshots`, `createRevision`) reach `getFilePathCandidates`, and `validatePathWithinBases` will throw rather than degrade when handed the wrong base. Worse, the `approval-change` broadcast handler (`multi-server.ts:404`) has no single requesting project by construction under Component 6 — so the "resolve at read time" story has no answer at the one site R10 AC 2 governs. Either exempt `ApprovalStorage` from sharing (keep one per project entry; it is the cheapest of the four — a debounced watcher over one directory — and R10's cost argument is dominated by `SpecWatcher` and the cleanup passes), or accept the signature change and enumerate all 16 call sites. Sharing it as described silently regresses the exact behaviour R11 AC 9 was written to protect.
