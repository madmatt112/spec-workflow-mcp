# Implementation Log: Task 11

**Summary:** Replaced the task 8 stubs at /runs and /runs/:projectId with the real shell Runs list, run page and Launch card (design C10 Runs and Launch card, D8, D11; Requirement 4). RunsPage lists NowModel.runs of enabled projects in Live (state live) and Ended (ended/stopped/exited) groups via the Group/Row primitives; each row shows project, spec, run id, state badge, phase and an age ticking each second; selecting a row navigates to /runs/<projectId>. A Launch chip in the header toggles one LaunchCard per enabled project (inline in RunsPage): the GET setup view's launchable spec, the saved setup overlaid on defaults in five summary lines (spec, supervisor, roles count, worktree, gates), a Launch button that POSTs buildLaunchInput(view) to the existing launch route, and an Edit setup table (supervisor model, model per role, provider for eligible roles, worktree, gates) that PUTs to the existing setup route. Launch is disabled with the reason when there is no launchable spec (disabledReason), a live run row exists, or launches[projectId].state is running/stopping; refusals render the 409 reason, the 400 field/error or the 500 step/detail via OpErrorView. RunPage holds the harness view for the route's project alone while mounted and renders from harness-model and harness-run-detail: the six-phase strip (version, rounds, approval date, live highlight); each open spawn's role/agent, declared (profile) and actual model, elapsed, last tool and an age badge marked past 15 minutes since lastActivityAt; a task table (id, title, status, verdict and tdd from the task-review summary route polled every 5 s while the spec has tasks, taskMeta risk and fix rounds) with status chips and the pager; rounds and spawns as two tables collapsed by default; and tabs Ledger (ledgerRows), Activity (activityRows) and Process log (harness-log lines, a reset batch replaces them), each with a text filter and a follow toggle that scrolls to new rows. The panel shows run id, start, code root, worktree, headless, providers, tokens and launch pid; a Stop button on the existing stop route enabled only while the launch state is running/stopping; and the setup route's saved else defaults as a collapsed table. A project with no ledger shows "no run for this project" with Stop disabled. Added a copy of the callHarness helper and buildLaunchInput/present/OpErrorView in shell/harness.tsx (the legacy HarnessPage.tsx is left untouched for task 13). Added shell.runs.* keys to en.json only; removed the two task 8 stubs. No new route, launch field or launch behaviour. Note: an external process rewrote RunsPage.tsx mid-task into a self-contained version that inlines the Launch card and setup table instead of importing a separate LaunchCard.tsx; the orphaned LaunchCard.tsx was removed so the committed tree is coherent.

### Integrations

#### Integration
- **Description:** The run page binds one project's harness view and renders live run detail from the project harness watch's pushes; a model, run-detail or log push refreshes the page with no reload.
- **Frontend Component:** RunPage (useWs().watchView({kind:'harness',projectId}); subscribe harness-model, harness-run-detail, harness-log)
- **Backend Endpoint:** /ws harness-subscribe -> ProjectHarnessWatch (harness-model, harness-run-detail, harness-log); GET /api/projects/:id/specs/:spec/task-reviews/summary polled every 5s; POST /api/projects/:id/harness/stop
- **Data Flow:** WebSocketProvider holds one /ws socket -> RunPage watchView(harness) sets connection.projectId and gets the hub snapshot -> harness-model (RunModel/profiles/launch), harness-run-detail (phaseStrip/taskMeta/ledgerRows/activityRows) and harness-log lines drive the strip, spawns, tables and log tabs; the task-review summary route supplies verdict/tdd; Stop calls the existing stop route

#### Integration
- **Description:** The Launch card fetches the per-project setup view, overlays the saved file on defaults and posts/saves through the existing harness routes with no new launch behaviour.
- **Frontend Component:** RunsPage LaunchCard/EditSetup (fetch GET /harness/setup; callHarness POST /harness/launch, PUT /harness/setup)
- **Backend Endpoint:** GET/PUT /api/projects/:id/harness/setup, POST /api/projects/:id/harness/launch
- **Data Flow:** LaunchCard GET setup view -> buildLaunchInput overlays saved supervisorModel/worktree/roles on defaults (spec=launchable) -> Launch POSTs it to the launch route exactly as the legacy Harness page did -> a 409/400/500 refusal body renders via OpErrorView; Edit setup PUTs the table's SetupInput and refetches the view
