## Summary

Implementation correctly fulfills R2.4/R2.13 and design steps 9-13: chunked async realpath, case-fold, set ops on normalized form with originals preserved, in-scope tagging, output-side denylist filtering with surfaced count, and 100-cap with in-scope-first ordering. Two warning-level findings concern silent drops on non-ENOENT realpath failures (allFiles entries vanish from both compiled and excluded; diagnostic-file errors collapse to inScope=false without distinction); one info notes the suppressed-files counter can over-count when the same physical file appears under distinct originals.

## Findings

### WARNING: Non-ENOENT realpath errors on allFiles entries are silently dropped from output
- **File:** src/core/typecheck.ts:223
- **Issue:** In postProcess (src/core/typecheck.ts:217-228), when an allFiles entry has a non-ENOENT realpath error, the `continue` skips it entirely — the original path appears neither in `compiled` nor in `excluded`. The warn-once does fire inside realpathChunked, but the reviewer's response payload silently loses the file. The task restriction states `all other realpath errors propagate via warn-once (do NOT silently swallow)`. Even though warn-once fires, the output-array semantics swallow the file: an EACCES/ELOOP path the agent claimed to modify disappears from the reviewer's coverage view with no structured signal. Consider routing these to `excluded` (matching ENOENT) or surfacing a separate `realpathErrors` count, so the reviewer can see the gap rather than infer it from log-once stderr.
- **Task Requirement:** Restriction: ENOENT realpath errors bucket as excluded, all other realpath errors propagate via warn-once (do NOT silently swallow)

### WARNING: Diagnostic-file realpath errors collapse to inScope=false without distinguishing ENOENT vs other
- **File:** src/core/typecheck.ts:240
- **Issue:** src/core/typecheck.ts:239-243 tags `inScope = norm !== undefined && allFilesNormalizedSet.has(norm)`. Any realpath failure on a diagnostic file (ENOENT or otherwise) simply yields `inScope=false`, with no warn-once fired here for non-ENOENT (warn-once does fire from realpathChunked, but only because the same code path is reused). There is no test case exercising the diagnostic-file realpath-error branch (test suite covers only allFiles ENOENT). A diag whose file legitimately matches an in-scope allFiles entry but realpath-fails for a non-ENOENT reason is silently demoted to out-of-scope and may then be deprioritized by the 100-cap ordering. Strictly speaking the restriction targets the allFiles path, but the same warn-vs-swallow tension exists here and is untested.
- **Task Requirement:** Restriction: all other realpath errors propagate via warn-once (do NOT silently swallow)

### INFO: suppressedDenylistedFiles counter can over-count when same physical file appears under multiple originals
- **File:** src/core/typecheck.ts:257
- **Issue:** src/core/typecheck.ts:253-257 builds the suppressed set as `caseFold(originalPath)` from compiledFilter/excludedFilter/diagFilter skipped lists. Because the dedupe key is the (case-folded) ORIGINAL path string — not the normalized realpath — the same denylisted file accessed via two different originals (e.g. via a symlink and its real path, or via different allFiles vs diagnostic representations on a case-sensitive volume) counts as two suppressed files. Spec language says `Surface dropped count as suppressedDenylistedFiles` — design does not pin the exact dedupe key, so this is a strict-interpretation issue rather than a hard violation, but the count can mislead a reviewer into thinking more distinct files were dropped than actually were.
- **Task Requirement:** design §src/core/typecheck.ts step 12 (surface dropped count as suppressedDenylistedFiles)
