## Findings

### INFO: Restriction uses async fs.mkdtemp instead of mkdtempSync
- **File:** /home/mcf/reference/spec-workflow-mcp/src/core/__tests__/task-diff.test.ts:59
- **Issue:** The task restriction explicitly specifies `mkdtempSync` for fixture repos, but the test uses `fs.mkdtemp` from `node:fs/promises` (line 13, 59). Behaviorally equivalent and arguably cleaner under async beforeEach, but technically diverges from the worded restriction. Worth a one-line note or a switch to the sync API for literal compliance.
- **Task Requirement:** Restriction: Use mkdtempSync + real git init for fixture repos

### WARNING [hygiene]: Per-file truncation test does not assert hunk replacement, only message presence
- **File:** /home/mcf/reference/spec-workflow-mcp/src/core/__tests__/task-diff.test.ts:199
- **Issue:** The per-file truncation test asserts `result.diff.toContain('<diff truncated: big.ts per-file cap exceeded>')` and `result.truncated === true`, but never asserts that the actual hunk lines were *replaced* by the message. The test would still pass if a future regression emitted both the truncation message AND the original 600-line hunks. Add an assertion like `expect(result.diff).not.toMatch(/^\+line 599/m)` or check the diff length stays small.
- **Task Requirement:** R1.9 — per-file truncation message

### WARNING [hygiene]: Binary-stripping test does not assert the binary file's diff header is removed
- **File:** /home/mcf/reference/spec-workflow-mcp/src/core/__tests__/task-diff.test.ts:179
- **Issue:** The binary-stripping test only checks that `Binary files ... differ` text is absent (line 179). The SUT actually strips the entire section (header + marker) for binary files, but the test never asserts `result.diff` does not contain `image.bin`. A regression that kept the `diff --git a/image.bin b/image.bin` header but stripped only the marker line would pass. Add `expect(result.diff).not.toContain('image.bin')`.
- **Task Requirement:** R1.5 — binary detection / R1.9 binary section stripping

### INFO [hygiene]: maxBuffer test claims to exercise ERR_CHILD_PROCESS_STDIO_MAXBUFFER but does not assert which error fired
- **File:** /home/mcf/reference/spec-workflow-mcp/src/core/__tests__/task-diff.test.ts:270
- **Issue:** The test at line 270 overrides `maxBuffer: 1024` and runs real git, then asserts only the degraded-state shape. The comment claims this exercises the genuine ERR_CHILD_PROCESS_STDIO_MAXBUFFER path, but if a future change made any unrelated error also trigger here (e.g. an exit-code change), the test would still pass. Consider intercepting the err passed to the execFile callback (or wrapping the callback to capture `err.code`) and asserting it equals `'ERR_CHILD_PROCESS_STDIO_MAXBUFFER'` — that pins the actual failure mode the comment promises.
- **Task Requirement:** Task description / Restriction: ERR_CHILD_PROCESS_STDIO_MAXBUFFER via maxBuffer:1024

### INFO [hygiene]: Total-budget truncation test does not pin which file the message names
- **File:** /home/mcf/reference/spec-workflow-mcp/src/core/__tests__/task-diff.test.ts:224
- **Issue:** The regex `/<diff truncated: .* total budget exhausted, file truncated despite size>/` matches any file token. Given pathspec ordering matters in the SUT (the SUT truncates remaining files in order once the budget is exhausted), the test could assert the *second or third* file's path appears in the message — verifying that earlier-in-pathspec files were emitted in full and only later ones got the budget-exhausted message. This would also catch a regression where the SUT inverts the ordering.
- **Task Requirement:** R1.9 — total-budget truncation message
