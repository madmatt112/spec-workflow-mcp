## Summary

Spawn contract, failure-mode taxonomy, cache-dir gate, env scrubbing, and timeout/maxBuffer behavior all match spec. Three warnings to action: 'rejection' reason orphaned in 5.1 scope, project-references gate over-triggers on empty array, and tsbuildinfo rebuild regex is broader than design's TS5083 signature.

## Findings

### WARNING: 'rejection' reason declared in TypecheckResult union but never produced in 5.1
- **File:** src/core/typecheck.ts:35
- **Issue:** spawnTsc swallows all errors via resolve(); no code path emits status='unavailable' with reason='rejection'. The orchestrator (task 8.2's unwrapTypecheck) sets it from a Promise.allSettled rejection — so 5.1 alone leaves the reason as a forward-declared placeholder. This is intentional given the architecture, but worth flagging so it doesn't read as a dead branch.
- **Task Requirement:** Success criterion: all 'unavailable' reasons reachable

### WARNING: project-references gate fires on empty references array
- **File:** src/core/typecheck.ts:79
- **Issue:** Array.isArray check matches `references: []` and emits 'project-references'. R2.1 / design step 2 intent is to gate on a non-empty references list (composite-build setups). Empty array should not gate — should fall through to the normal tsc invocation.
- **Task Requirement:** R2.1 / design step 2

### WARNING: tsbuildinfo rebuild regex broader than design's TS5083 signature
- **File:** src/core/typecheck.ts:50
- **Issue:** Regex /TS5083|tsbuildinfo/i triggers the typecheckWarning on any stderr mentioning 'tsbuildinfo' (case-insensitive). Design line 187 names TS5083 (and 'matching rebuild messages') as the signature. Pure literal 'tsbuildinfo' match risks surfacing the warning when the rebuild did not actually occur.
- **Task Requirement:** design line 187

### INFO [hygiene]: JSONC line-comment stripper can mangle '//' inside string values
- **File:** src/core/typecheck.ts:158
- **Issue:** Regex `(^|[^:])//[^\n]*` avoids `http://` via the `[^:]` lookback but not `//server/share` inside a JSON string value. Acceptable for typical tsconfigs but a known sharp edge.

### INFO [hygiene]: shell:true on Windows widens injection surface for projectPath
- **File:** src/core/typecheck.ts:223
- **Issue:** execFile uses `shell: true` on win32 to run `tsc.cmd`. Path values are constructed from projectPath; shell-meta chars in projectPath would be interpreted by cmd.exe. Low risk in practice — projectPath is user-trusted — but worth noting for cross-platform deployments.

### INFO [hygiene]: Non-numeric error.code yields exitCode=null, conflating spawn-fail with parse-fail
- **File:** src/core/typecheck.ts:236
- **Issue:** When execFile error.code is a string (e.g. 'ENOENT' for spawn failure), exitCode becomes null and downstream returns 'no-parseable-output'. Distinct error classes coalesce. Doesn't affect reachability claims; just means a missing tsc that slipped past resolveTscBinary would be reported as parse-fail rather than tsc-not-found.
