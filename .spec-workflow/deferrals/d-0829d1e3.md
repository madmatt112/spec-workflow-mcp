## Context
Scoping worktree-execution-context, the plan considered four phases: (0) correct workspace identity, (1) thread workspacePath to code-touching operations, (2) repoId grouping in the registry and dropdown, (3) per-worktree badges. Phases 0+1 fix the correctness defect; 2+3 are UX. ORIGINAL RATIONALE WAS WRONG and has been corrected: the first version of this deferral claimed the existing 'repo · worktree' naming was sufficient. The v2 adversarial review disproved that — ProjectManager.addProject builds SpecParser, SpecWatcher, ApprovalStorage and SpecArchiveService per registry entry from the workflow root (src/dashboard/project-manager.ts:146-152), so correct identity would have produced N full copies of every spec/approval/task view, N recursive cleanup passes over one directory, and N SSE broadcasts per file change. That is a content-duplication problem, not a naming problem. Requirement 10 now shares those components per workflowRootPath, which removes the duplicated work, watchers, and cleanup passes. What remains deferred is only the UI: the dropdown still lists one flat entry per worktree instead of nesting worktrees under a repo, and approvals/tasks/jobs carry no worktree badge.

## Decision Deferred
Not building repoId-based grouping in the project dropdown, nested worktree display under a repo, or per-worktree badges on approvals, task rows, and review jobs.

## Revisit Criteria
Flat dropdown unusable at observed worktree counts, or worktree attribution of approvals/jobs requested. Requirement 8 (workspace recorded in implementation logs) and Requirement 9 (execution context in review prompts) already supply the data a badge would display, so the UI work would be additive.
