## Context
Surfaced by the task 4 reviewer. AC 6.6 says this spec's lock "SHALL cover the registry writers only" — plural — while AC 6.1 names registerProject specifically and Requirement 6's design note justifies the lock solely by the lost-registration race that per-worktree identity creates. Read in context, 6.6 is a scope limit contrasting the registry against the four other shared-root files owned by worktree-dashboard-concurrency, not an instruction to lock every registry function; task 4 was implemented as written and its scope is defensible. But the ambiguity is real, and the symmetric hazard is real: unregisterProject, unregisterProjectById and cleanupStaleProjects all read-modify-write activeProjects.json unlocked, so N worktrees stopping concurrently can lose a removal the same way N starting could lose a registration. This spec's task 15 adds unregisterProjectById and calls it from stop(), so spec 1 does touch the unregister path even though it does not lock it.

## Decision Deferred
Not decided: whether unregisterProject, unregisterProjectById and cleanupStaleProjects also need the exclusive lock, and which spec owns that. Task 4 locked registerProject only, per AC 6.1.

## Revisit Criteria
worktree-dashboard-concurrency writes requirements covering R11 locking, or a lost-unregistration bug is observed in multi-worktree use.
