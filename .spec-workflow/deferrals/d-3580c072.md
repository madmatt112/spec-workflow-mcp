## Context
Found while rewriting the worktree e2e harness in task 16. The dashboard watches activeProjects.json with chokidar, and the watch is established on the parent directory. An `rm -rf $SPEC_WORKFLOW_HOME` between test suites — the obvious way to isolate them — permanently kills that watch for the life of the process: later suites then time out waiting for registrations that in fact succeeded, because the dashboard never learns about them. The failure presents as a flaky or hanging test rather than as anything pointing at the watch, so it costs real debugging time. Task 16 avoided it by adding resetSpecWorkflowHome, which empties the directory instead of removing it. The same trap applies to any future harness in worktree-review-signals or worktree-dashboard-concurrency, and arguably to real usage: a user who deletes and recreates their global directory while the dashboard is running gets a silently dead watch.

## Decision Deferred
Not decided: whether the dashboard should re-establish its activeProjects.json watch when the global directory is recreated, or whether test harnesses must simply never delete it. Task 16 worked around it with a resetSpecWorkflowHome helper that empties rather than removes the directory.

## Revisit Criteria
worktree-dashboard-concurrency drafts requirements covering the global directory location or watcher lifecycle, or a new e2e harness needs suite isolation.
