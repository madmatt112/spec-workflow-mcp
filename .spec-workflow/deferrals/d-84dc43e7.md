## Context
Observed at the tighter-reviews end-to-end verification gate. npm run test:e2e:worktree passes 9/9 from a clean SPEC_WORKFLOW_HOME, verified twice. An immediate REPEAT run against the retained state directory fails 1 of 9 — worktree-shared.spec.ts:394, a specs-list HTTP call. The failure is off the tighter-reviews code path entirely and is harness state contamination rather than a product defect, so it did not block the gate. It is plausibly related to d-3580c072 and d-4ee04d64, which both concern the dashboard's registry watcher and the global directory lifecycle: a retained state directory carries registry entries from the prior run, and the watcher's behaviour across that boundary is exactly what those two deferrals describe. Worth resolving together rather than separately. The practical impact today is that a developer re-running the worktree suite without clearing state sees a confusing single-test failure that does not reproduce from clean.

## Decision Deferred
Not decided: whether the worktree e2e harness should reset its SPEC_WORKFLOW_HOME state between runs, or whether the suite should be documented as requiring a clean state directory each time.

## Revisit Criteria
worktree-dashboard-concurrency drafts requirements covering the global directory or watcher lifecycle, or the worktree e2e suite is extended with new scenarios.
