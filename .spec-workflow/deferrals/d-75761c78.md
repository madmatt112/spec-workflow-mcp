## Context
The v1 adversarial review on worktree-execution-context requirements asked for tasks.md concurrency handling; v2 showed the acceptance criteria added in response protected the wrong writer. The only in-repo tasks.md writer is the single-process dashboard endpoint (src/dashboard/multi-server.ts:1445-1446, via updateTaskStatus at src/core/task-parser.ts:342), which does not race. Agents set task status by editing the file directly with their own editor tools, exactly as spec-workflow-guide.ts instructs, so no server-side read-retry-write can mediate it. Closing this properly needs a task-status MCP tool plus a change to the workflow guide so agents call it instead of editing — a feature addition that was not costed in this spec. Deferred in favour of stating the limitation plainly (Requirement 11 AC 7) rather than shipping criteria that read as protection the architecture cannot provide. Note this same gap is why Requirement 5 AC 8 exists: no diff base can be recorded at task start when the status change never reaches the server.

## Decision Deferred
Not adding a task-status MCP tool, and not routing agent task-status changes through the server. Concurrent edits to a shared tasks.md from multiple worktrees can silently lose data, and worktree-execution-context does not close this.

## Revisit Criteria
Observed data loss in tasks.md from concurrent agents, or a second feature blocked on lacking a task-start hook. Requirement 5 AC 1 already defines what such a hook would record, so the tool would have a concrete first consumer.
